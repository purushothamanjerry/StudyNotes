Database Security — Locking the Vault, Not Just the Door

An application's front door can be perfectly guarded, but if the database behind it trusts every query blindly, stores passwords in plain text, or hands every user full access — the vault was never actually locked.

The classic attack:
-- Login form concatenates raw input:
"SELECT * FROM users WHERE username='" + input + "'"

-- Attacker types: admin' -- 
SELECT * FROM users WHERE username='admin' --';
The -- comments out the password check entirely. One string, no password needed, full account takeover — this is SQL Injection, and this module is about the layered defenses that stop it and everything like it.
01

Why Database Security Exists

The database usually holds the most valuable, most sensitive data in the entire system — user identities, financial records, health data. A single weak point (unsanitized input, an over-privileged account, plaintext passwords) can expose all of it at once.

Problem it solves

Untrusted input

Any value coming from a user, API, or file could be malicious — the database layer can't assume otherwise.

Blast radius

A compromised app account with full DB rights can drop tables; a least-privilege account limits the damage.

Accountability & recovery

When something does go wrong, audit logs and backups are what let you find out what happened and undo it.

Interview one-liner

"Database security is layered: prevent injection at the query layer, limit privileges at the account layer, protect data at rest and in transit, and keep logs and backups so you can detect and recover from whatever still gets through."

02

SQL Injection

Occurs when untrusted input is concatenated directly into a SQL string, letting an attacker change the query's actual logic instead of just supplying a data value.

-- Vulnerable Java (string concatenation):
String sql = "SELECT * FROM users WHERE username='" + username +
             "' AND password='" + password + "'";
Statement stmt = conn.createStatement();
stmt.executeQuery(sql);

-- Attacker input: username = admin' -- 
-- Resulting query: SELECT * FROM users WHERE username='admin' -- ' AND password='...'
-- Everything after -- is a comment: password check is gone

Beyond login bypass

  • UNION-based: appending UNION SELECT to pull data from other tables entirely.
  • Stacked queries: appending ; DROP TABLE users; to run a second, destructive statement.
  • Blind injection: inferring data one bit at a time from true/false or timing differences when no output is shown directly.
Interview trap

"Does escaping quotes fully solve SQL injection?" — No. Manual escaping is fragile and easy to get wrong across contexts (numeric fields, LIKE patterns, ORDER BY column names). Parameterized queries (prepared statements) are the actual fix, not string sanitization.

03

Prepared Statements

The query's structure is sent to MySQL separately from the data values, with placeholders (?) marking where values go. The database compiles the query shape first — user input can never be interpreted as SQL syntax, only as a literal value.

-- Java / JDBC (safe):
String sql = "SELECT * FROM users WHERE username=? AND password=?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, username);
ps.setString(2, hashedPassword);
ResultSet rs = ps.executeQuery();

-- Raw SQL equivalent:
PREPARE stmt FROM 'SELECT * FROM users WHERE username=? AND password=?';
SET @u = 'admin', @p = 'hash...';
EXECUTE stmt USING @u, @p;

Even if the attacker enters admin' --, it's bound as the literal string value for username — MySQL will simply look for a user literally named admin' --, which won't exist.

Best practice

In Spring Data JPA, using method-derived queries, @Query with named parameters, or the Criteria API already parameterizes correctly — the risk mainly appears when someone drops down to native, string-concatenated SQL.

Least Privilege

Every account — human or application — should hold only the exact privileges it needs to do its job, and nothing more. If that account is ever compromised, the damage is capped by what it was allowed to touch.

App's DB user

SELECT/INSERT/UPDATE/DELETE on its own schema's tables only — never DROP, never access to other applications' schemas.

Reporting/BI user

SELECT-only, often restricted to specific views rather than raw base tables.

DBA/admin user

Full privileges, but used rarely, with its own audited login — never the account the application itself connects with.

Interview one-liner

"Least privilege means an application never connects to the database as root — it gets a narrowly scoped account matching exactly what its code needs to do."

06

Roles

A role is a named collection of privileges that can be granted to (and revoked from) multiple users at once, instead of managing each privilege per user individually.

CREATE ROLE app_read_only;
GRANT SELECT ON mydb.* TO app_read_only;

CREATE ROLE app_read_write;
GRANT SELECT, INSERT, UPDATE, DELETE ON mydb.* TO app_read_write;

-- assign roles to actual users
GRANT app_read_only TO 'analyst'@'%';
GRANT app_read_write TO 'app_user'@'%';

-- activate the role for the session
SET DEFAULT ROLE app_read_write TO 'app_user'@'%';
Best practice

Define roles once around job functions ("reporting", "app-write", "migration-admin"), then grant/revoke roles to users instead of managing dozens of individual GRANT statements per person.

07

GRANT

Gives a user or role specific privileges on a specific scope — globally, on a database, a table, or even individual columns.

GRANT SELECT, INSERT, UPDATE ON mydb.orders TO 'app_user'@'%';
GRANT SELECT (id, name, dept_id) ON mydb.employees TO 'app_user'@'%'; -- column-level
GRANT ALL PRIVILEGES ON mydb.* TO 'dba_admin'@'localhost';
FLUSH PRIVILEGES; -- reload grant tables when needed
Interview one-liner

"GRANT syntax reads as: give these privileges, on this scope, to this user — and scope can be as broad as *.* or as narrow as a single column."

08

REVOKE

The exact mirror of GRANT — removes specific privileges from a user or role without necessarily removing the account itself.

REVOKE INSERT, UPDATE ON mydb.orders FROM 'app_user'@'%';
REVOKE ALL PRIVILEGES, GRANT OPTION FROM 'old_employee'@'%';
DROP USER 'old_employee'@'%'; -- fully remove the account
Beginner mistake

Deleting a user account without first checking what objects (views with DEFINER security, scheduled events) depended on it — REVOKE-and-review before DROP USER in production.

09

Password Storage

Application passwords must never be stored in plain text or with reversible encryption — they should be run through a slow, salted, one-way hashing algorithm designed specifically for passwords.

ApproachSafe?Why
Plain textNeverA single DB leak exposes every password directly.
MD5 / SHA-1 (unsalted)NeverFast to compute — attackers brute-force or use rainbow tables.
SHA-256 (unsalted)NoStill fast; identical passwords produce identical hashes.
bcrypt / scrypt / Argon2 (salted)YesDeliberately slow, salted per-user, resistant to brute force and rainbow tables.
// Spring Security — BCrypt (application layer, not raw SQL)
BCryptPasswordEncoder encoder = new BCryptPasswordEncoder();
String hashed = encoder.encode(rawPassword);
// store `hashed`, never `rawPassword`, in the users table
Interview one-liner

"Password hashing must be one-way and salted, and use a deliberately slow algorithm like bcrypt or Argon2 — never a general-purpose fast hash like MD5 or plain SHA-256."

10

Encryption

Encryption in transit

TLS/SSL between the application and MySQL, so credentials and data can't be sniffed on the network.

jdbc:mysql://host:3306/db?useSSL=true&requireSSL=true

Encryption at rest

InnoDB's Transparent Data Encryption (TDE) encrypts tablespace files on disk, so a stolen disk/backup file alone isn't readable.

ALTER TABLE employees ENCRYPTION='Y';
Interview one-liner

"In transit protects data on the wire (TLS); at rest protects data on disk (TDE) — a complete design uses both, since each protects against a different attack surface."

11

Audit Logs

A recorded, tamper-resistant trail of who did what to the database and when — logins, privilege changes, and (selectively) data access — used for detecting misuse and for compliance.

-- MySQL Enterprise Audit plugin (or open-source alternatives like MariaDB Audit Plugin)
INSTALL PLUGIN audit_log SONAME 'audit_log.so';
SET GLOBAL audit_log_policy = 'ALL';

What's typically logged

Login attempts (success/fail)Privilege/GRANT changesSchema changes (DDL)Sensitive table accessFailed queries

Best practice

Ship audit logs to a separate, append-only system the database's own admins can't quietly edit — an audit trail that the attacker (or a rogue insider) can erase isn't much of a trail.

12

Backup & Restore

Security isn't only about preventing breaches — it's also about surviving ransomware, accidental DROP TABLEs, and hardware failure. A tested backup is the last line of defense.

-- Logical backup (portable, human-readable)
mysqldump -u root -p --single-transaction mydb > backup.sql

-- Restore
mysql -u root -p mydb < backup.sql

-- Physical backup (faster for large DBs) — Percona XtraBackup / MySQL Enterprise Backup

--single-transaction

Takes a consistent InnoDB snapshot without locking the whole database during the dump.

Encrypt backups too

A backup file is a full copy of your data — it needs the same at-rest protection as the live database.

Interview trap

"Is having a backup enough?" — No. An untested restore process is not a real backup strategy; teams should periodically actually restore from backup to confirm it works.

13

Spring Boot Relation

  • Spring Data JPA / JdbcTemplate parameterize queries by default — the SQL injection risk mainly shows up when a developer builds native SQL with string concatenation instead of ? placeholders or named parameters.
  • Spring Security's PasswordEncoder (BCrypt by default) handles password hashing so raw passwords never reach the database layer.
  • application.properties should point at a least-privilege database user, never a superuser, and secrets should come from a vault/secret manager, not committed config.
// Vulnerable: never do this
String sql = "SELECT * FROM users WHERE username='" + name + "'";
jdbcTemplate.queryForObject(sql, User.class);

// Safe: named/positional parameters
jdbcTemplate.queryForObject(
  "SELECT * FROM users WHERE username = ?", User.class, name);
Interview angle

"Where in a Spring Boot app is SQL injection risk usually introduced despite using JPA?" — Native queries built with string concatenation, dynamic ORDER BY/column names built from raw input, or JPQL/@Query strings interpolating values directly instead of using :paramName or ?1.

14

Advantages · Disadvantages · When to Apply

Advantages

Prevents catastrophic data breaches · limits blast radius of a compromised account · provides accountability (audit logs) and recoverability (backups) when something still goes wrong.

Disadvantages / costs

More operational overhead (managing roles/grants) · encryption adds some CPU cost · audit logging adds storage and I/O overhead if over-configured.

Always apply

Prepared statements, least privilege, password hashing — there is essentially never a valid reason to skip these.

Apply based on risk profile

Full audit logging and at-rest encryption scale with how sensitive the data is (PII, financial, health data) and any compliance requirements (GDPR, PCI-DSS, HIPAA).

15

Best Practices & Beginner Mistakes

Beginner mistake

Connecting the application to MySQL as root "to avoid permission errors." This means a single SQL injection or leaked credential compromises the entire server, not just one schema.

Beginner mistake

Building dynamic ORDER BY or column names from raw user input, assuming prepared statements alone protect it — parameter placeholders work for values, not identifiers, so column/table names must be validated against an allow-list instead.

Best practice

Layer your defenses: parameterized queries + least privilege + hashed passwords + encryption + audit logs + tested backups. No single control is sufficient on its own — this is "defense in depth."

Interview, Scenario & Company Questions

What is SQL injection, in one sentence?+
Untrusted input being interpreted as part of the SQL query's structure instead of as a plain data value, letting an attacker alter the query's logic.
Why are prepared statements the real fix, not just escaping quotes?+
Escaping is manual and context-dependent (easy to miss a case); prepared statements send query structure and data separately so user input can never be parsed as SQL syntax at all.
What's the difference between GRANT and REVOKE?+
GRANT gives a user/role specific privileges on a specific scope; REVOKE removes previously granted privileges — they are exact mirrors of each other.
A search feature lets users sort results by any column name via a query parameter. How do you keep this safe?+
Prepared statement placeholders don't work for identifiers like column names — validate the requested column against a fixed allow-list of known-safe column names before building the ORDER BY clause.
You inherit a legacy app where the DB user has ALL PRIVILEGES. How do you migrate to least privilege safely?+
Audit which actual queries the app runs (via logs), create a new role granting exactly those privileges, test in staging, then switch the connection string and revoke the old broad grants.

ZohoTCS DigitalInfosysAccentureCapgeminiCognizantHCLWipro

[Zoho / Product companies] How would you securely store user passwords in a new signup feature?+
Hash with a slow, salted algorithm like bcrypt or Argon2 at the application layer before storage; never store or log the raw password; never use a fast general-purpose hash like MD5/SHA-256 alone.
[TCS Digital / Infosys] What is the principle of least privilege and why does it matter?+
Every account gets only the minimum privileges needed for its job — it limits how much damage a compromised credential or bug can cause.
[Accenture / Capgemini / Cognizant] Why encrypt both in transit and at rest — isn't one enough?+
They protect against different threats: in-transit encryption stops network sniffing, at-rest encryption stops exposure from a stolen disk or backup file — a complete design needs both.

SQL Practice Questions

1. Create a read-only role and grant it to a new reporting user.+
Answer
CREATE ROLE reporting_ro;
GRANT SELECT ON mydb.* TO reporting_ro;
CREATE USER 'analyst1'@'%' IDENTIFIED BY 'StrongPass!23';
GRANT reporting_ro TO 'analyst1'@'%';
SET DEFAULT ROLE reporting_ro TO 'analyst1'@'%';
2. Grant an app user privileges on only the orders and customers tables (nothing else in the schema).+
Answer
GRANT SELECT, INSERT, UPDATE ON mydb.orders TO 'app_user'@'%';
GRANT SELECT, INSERT, UPDATE ON mydb.customers TO 'app_user'@'%';
3. Revoke DELETE privilege from an app user who should never delete data.+
Answer
REVOKE DELETE ON mydb.* FROM 'app_user'@'%';
4. List all privileges currently granted to a given user.+
Answer
SHOW GRANTS FOR 'app_user'@'%';
19

Memory Tricks

"? = Question, not Command"

A placeholder in a prepared statement is always treated as a question to answer with data — never as an instruction to execute.

Least Privilege = "borrow, don't own"

An account should only ever hold exactly what it needs to borrow for its job, never own the whole vault.

Backup = "the last undo button"

Every other control (locks, grants, encryption) can fail — a tested backup is what still saves you.

Summary

Database security is layered defense: prepared statements stop SQL injection at the query layer; least privilege, roles, GRANT and REVOKE limit what a compromised account can do; password hashing and encryption (in transit and at rest) protect the data itself; audit logs provide accountability; and tested backups are the final safety net when everything else fails.

Revision Notes

  • SQL injection = untrusted input becomes part of query syntax
  • Prepared statements separate query structure from data — the real fix, not escaping
  • Least privilege: app never connects as root/superuser
  • Roles bundle privileges for reuse across users
  • GRANT / REVOKE are exact mirrors, scoped from global to column-level
  • Passwords: bcrypt/Argon2, salted, slow — never plain text or fast unsalted hashes
  • Encryption: TLS in transit, TDE at rest — different threats, need both
  • Audit logs: tamper-resistant, shipped off-system
