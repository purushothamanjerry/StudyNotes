01

SQL Overview

Before memorising syntax, an interviewer wants to know you understand why SQL exists at all.

Why this topic exists

Applications need to store data that outlives the running process — user accounts, orders, inventory. Early on, every application invented its own file format to do this, which was slow, unsafe under concurrent access, and impossible to query flexibly. Relational databases standardised storage into tables, and SQL (Structured Query Language) became the single language to define, change, query, secure, and commit that data — regardless of which vendor's database you use underneath.

Problem it solves

  • Gives a declarative way to ask "what data I want" without writing the retrieval algorithm yourself.
  • Provides ACID guarantees so concurrent users don't corrupt each other's data.
  • Separates structure (schema) from data (rows), so both can evolve independently.
  • Works identically in spirit across MySQL, PostgreSQL, Oracle, SQL Server — one skill, many databases.

Real-world example

Think of a bank. The schema is the printed passbook format (columns: date, description, amount, balance) — that's DDL. Writing a new transaction into the passbook is DML. Reading last month's transactions is DQL. Deciding which teller is allowed to edit vs only view is DCL. And the bank finalising a batch of transactions atomically at day-end (either the whole batch posts, or none of it does) is TCL.

Simple Explanation

SQL is a set of commands to create tables, put data in them, read data out, control who can touch them, and save/undo changes.

Interview Explanation

"SQL is divided into sub-languages by responsibility — DDL for structure, DML for data, DQL for retrieval, DCL for permissions, TCL for transaction control. MySQL implements all five on top of the InnoDB storage engine by default."

Interview Tip

If asked "Is SQL a programming language?" — answer: it's a declarative language (you describe the result, not the steps), not a procedural/general-purpose language. MySQL adds procedural extensions on top for stored procedures.

03

DDL — Data Definition Language

Commands that define, change, or remove the structure of database objects — tables, schemas, indexes, views.

How MySQL internally works

Every DDL statement updates MySQL's data dictionary (in modern MySQL 8+, stored in transactional InnoDB tables instead of old .frm files). Because structural changes historically couldn't be rolled back safely, MySQL issues an implicit COMMIT before and after most DDL statements — this is why DDL is said to "auto-commit," even inside an open transaction.

ddl_examples.sql
CREATE TABLE employee (
  id INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(100) NOT NULL,
  salary DECIMAL(10,2)
);

ALTER TABLE employee ADD email VARCHAR(150);
ALTER TABLE employee MODIFY salary DECIMAL(12,2);

TRUNCATE TABLE employee;   -- wipes rows, keeps structure
DROP TABLE employee;      -- removes structure + data
Common Mistake

Confusing DROP with TRUNCATE, or TRUNCATE with DELETE. DROP removes the table entirely (schema gone); TRUNCATE keeps schema but resets identity/auto-increment; DELETE (DML) keeps schema, keeps auto-increment counter, and can be rolled back.

Best Practice

Never run destructive DDL (DROP/TRUNCATE) directly against production. Use migration tools (Flyway/Liquibase in Spring Boot projects) so schema changes are versioned and reviewable.

04

DML — Data Manipulation Language

Commands that add, change, or remove rows — the structure stays untouched.

dml_examples.sql
INSERT INTO employee (name, salary) VALUES ('Asha', 55000);

UPDATE employee
SET salary = salary * 1.1
WHERE id = 4;

DELETE FROM employee WHERE salary < 20000;
✓ 1 row inserted → Query OK, 1 row affected (0.01 sec)
idnamesalary
4Asha60500.00

Deep explanation

DML statements are logged in InnoDB's transaction log and are not permanent until a COMMIT happens (or autocommit mode — MySQL's default — commits each statement automatically). This is exactly why understanding TCL alongside DML matters: without an explicit transaction, every INSERT/UPDATE/DELETE commits itself immediately in default MySQL config.

Warning

An UPDATE or DELETE without a WHERE clause applies to every row in the table. This is one of the most common production incidents fresher engineers cause — always run the equivalent SELECT with the same WHERE first.

05

DQL — Data Query Language

Technically just one keyword — SELECT — but it is the most interviewed statement in all of SQL.

dql_example.sql
SELECT department, COUNT(*) AS headcount
FROM employee
WHERE salary > 30000
GROUP BY department
HAVING COUNT(*) > 2
ORDER BY headcount DESC
LIMIT 5;
departmentheadcount
Engineering14
Sales9
Support3

This exact query is also our launchpad for the next section — every clause above runs in a different order than it's written. That mismatch between written order and execution order is one of the most-asked MySQL fundamentals in interviews.

06

DCL — Data Control Language

Controls who can do what — the security layer of SQL.

dcl_example.sql
GRANT SELECT, INSERT ON company.employee TO 'app_user'@'%';
REVOKE INSERT ON company.employee FROM 'app_user'@'%';
FLUSH PRIVILEGES;

Real-world analogy: DCL is the bank manager deciding which teller role can view balances vs. authorise withdrawals. In production, a Spring Boot application typically connects using a dedicated MySQL user with only the exact privileges its service needs — never the root account.

Beginner Mistake

Using the root MySQL user in an application's application.properties. If credentials leak, the attacker gets full DDL+DML+DCL power instead of a scoped subset.

07

TCL — Transaction Control Language

Groups multiple DML statements into one atomic unit of work — the backbone of ACID.

tcl_example.sql
START TRANSACTION;

UPDATE account SET balance = balance - 500 WHERE id = 1;
SAVEPOINT before_credit;
UPDATE account SET balance = balance + 500 WHERE id = 2;

-- if anything looks wrong:
ROLLBACK TO before_credit;

COMMIT;

Real-world example: a bank transfer of ₹500 must debit one account and credit another together. If the credit step fails after the debit succeeded, TCL lets you ROLLBACK the whole unit so money isn't lost mid-transfer. This maps directly to Spring's @Transactional annotation, which under the hood issues these exact COMMIT/ROLLBACK calls through JDBC.

Interview Tip

Be ready to state the 4 ACID properties from memory: Atomicity, Consistency, Isolation, Durability — and that TCL is how MySQL exposes Atomicity to the developer.

09

Common Mistakes & Performance Notes

Click to expand each pitfall.

Forgetting WHERE on UPDATE/DELETE ▾
Updates/deletes every row in the table. Always test the WHERE clause with a SELECT first, and consider enabling MySQL's Safe Update Mode during development.
Using SELECT * in production code ▾
Pulls unnecessary columns, breaks when schema changes, and prevents MySQL from using a covering index. Always name the columns you need.
Mixing DDL inside a transaction expecting rollback ▾
DDL implicitly commits, so a ROLLBACK after a CREATE/ALTER/DROP won't undo it — only the DML around it.
No index on foreign key / WHERE columns ▾
Causes full table scans. Use EXPLAIN to check if MySQL's optimizer is using an index, and add one on columns used in WHERE, JOIN, and ORDER BY frequently.
Confusing HAVING with WHERE ▾
WHERE filters rows before grouping; HAVING filters groups after aggregation. You cannot use an aggregate function like COUNT() inside WHERE.

Performance Notes

  • Index columns used in WHERE, JOIN, GROUP BY and ORDER BY — but don't over-index; every index slows down INSERT/UPDATE.
  • Prefer batch INSERTs (multi-row VALUES) over one INSERT per row from application code.
  • Use EXPLAIN before assuming a query is slow because of the database rather than the query itself.

Security Notes

  • Always use parameterised queries / PreparedStatement (JDBC) to prevent SQL injection — never string-concatenate user input into SQL.
  • Grant least-privilege access via DCL; avoid using the root account from an application.

Interview Tip

A very common fresher question: "What happens if an exception is thrown inside a @Transactional method?" Answer: Spring rolls back the transaction automatically for unchecked (RuntimeException) exceptions by default — this is TCL happening under the hood.

11

Advantages, Disadvantages & When to Use

  • Declarative — you describe the "what," MySQL's optimizer figures out the "how."
  • Strong ACID guarantees for critical, structured, relational data.
  • Mature tooling, huge community, first-class Spring Data JPA support.
  • Rigid schema — changing structure at scale needs careful migration planning.
  • Vertical scaling is easier than horizontal scaling compared to some NoSQL stores.
  • Complex joins across many tables can become a performance bottleneck if unindexed.
  • Structured, relational data with clear entities and relationships (orders, users, payments).
  • Applications needing strong consistency and transactions (banking, inventory, bookings).
  • Highly unstructured or rapidly changing schemas (consider document stores like MongoDB).
  • Massive horizontal write scaling needs where eventual consistency is acceptable.

SQL Practice Questions

Write a query to find the 2nd highest salary in employee ▾

Expected Answer:

SELECT MAX(salary)
FROM employee
WHERE salary < (SELECT MAX(salary) FROM employee);

Alternative: SELECT DISTINCT salary FROM employee ORDER BY salary DESC LIMIT 1 OFFSET 1;

Delete duplicate rows keeping the lowest id ▾
DELETE e1 FROM employee e1
JOIN employee e2
  ON e1.email = e2.email AND e1.id > e2.id;
Get department-wise average salary above company average ▾
SELECT department, AVG(salary) AS avg_sal
FROM employee
GROUP BY department
HAVING AVG(salary) > (SELECT AVG(salary) FROM employee);

Summary

SQL splits into five responsibility-driven families. DDL shapes tables and auto-commits; DML changes rows and needs an explicit or automatic commit; DQL (SELECT) reads data and runs FROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BY→LIMIT internally, not top-to-bottom as written; DCL secures access; TCL wraps DML into atomic, all-or-nothing units. Spring Boot leans on JPA/Hibernate and @Transactional to generate most of this SQL for you — but every interviewer expects you to know what's happening underneath.
