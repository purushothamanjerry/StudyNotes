Creating Databases & Tables

Every backend system starts with a blueprint before it becomes a building. In MySQL, that blueprint is DDL — CREATE, ALTER, DROP, TRUNCATE, RENAME. This module makes you interview-ready on how schemas are actually laid down, stored, and evolved in production.

Why this module exists

Before any query runs, someone had to build the room

SELECT, JOIN, and INDEX questions get all the attention — but almost every fresher interview opens with a DDL question, because it reveals whether you actually understand how a schema is designed, not just how to query one.

Problem it solves

Without DDL, there is no structure for data to live in. DDL (Data Definition Language) is how you tell MySQL: "here is the shape of my data, here are the rules it must obey." It defines databases, tables, columns, types, and constraints — the container before the content.

Real-world analogy

A database is a building site. CREATE DATABASE pours the foundation. CREATE TABLE builds a room with labeled compartments (columns) of fixed shape (data types). ALTER renovates the room without demolishing it. DROP demolishes it. TRUNCATE empties the room but keeps its walls.

Interview framing

Interviewers use DDL questions as a filter question early on. If you can clearly explain DROP vs TRUNCATE vs DELETE, or CHAR vs VARCHAR, it signals you've actually used MySQL — not just memorized SELECT syntax from a tutorial.

01 · Statement

CREATE DATABASE

The first command in any MySQL system's life — it allocates a named namespace where every table, view, and stored procedure for a project will live.

01Explanation, three ways

Simple

A database is a folder that groups related tables together. CREATE DATABASE makes that folder.

Technical

MySQL creates a schema entry and, on disk, a directory under the data directory (e.g. /var/lib/mysql/company_db). Since MySQL 8, table metadata lives in a transactional data dictionary instead of loose .frm files.

Interview

Say this: "In MySQL, DATABASE and SCHEMA are synonyms — unlike Oracle or PostgreSQL where a schema is a namespace inside a database." This one line is asked constantly.

create_database.sql
CREATE DATABASE IF NOT EXISTS company_db
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

SHOW DATABASES;
USE company_db;
→ Query OK, 1 row affected
→ Database company_db created on disk at /var/lib/mysql/company_db
→ Default character set: utf8mb4 (full Unicode incl. emoji, 4 bytes/char)

02How MySQL works internally

1

Parser validates syntax

MySQL checks the statement is valid SQL and the database name doesn't collide with a reserved system schema.

2

Directory created on disk

A physical directory is created under the data directory to hold future table files.

3

Entry added to data dictionary

MySQL 8+ records the schema, its default charset and collation in the internal data dictionary tables.

4

Available via USE / fully-qualified names

You can now switch context with USE company_db; or reference tables as company_db.employees.

Common Mistake

Forgetting IF NOT EXISTS in scripts that may re-run (CI/CD, seed scripts) — this throws Error 1007: database exists and breaks idempotent deployment scripts.

Best Practice

Always set an explicit charset/collation (utf8mb4) at creation time. Relying on the server default risks storing 3-byte UTF-8 that silently breaks on emoji or certain Asian scripts.

03Interview questions

Is there a difference between DATABASE and SCHEMA in MySQL?+

No — MySQL treats them as synonyms. CREATE SCHEMA and CREATE DATABASE do exactly the same thing. This differs from PostgreSQL/Oracle, where a schema is a sub-namespace inside a database.

What happens if you CREATE DATABASE without IF NOT EXISTS on an existing name?+

MySQL throws ERROR 1007 (HY000): Can't create database 'x'; database exists. Using IF NOT EXISTS suppresses the error and makes the script safely re-runnable.

Scenario: Your Spring Boot app fails to start with "Unknown database". What's the fix? Scenario+

The database referenced in spring.datasource.url doesn't exist yet. Either run CREATE DATABASE manually before startup, or add createDatabaseIfNotExist=true to the JDBC URL for local/dev environments (never in production).

02 · Statement

CREATE TABLE

The single most-asked DDL topic in fresher interviews — because it packs constraints, keys, engines, and data types into one statement.

Real-world analogy

A table is a spreadsheet with strict rules: every row must have the same columns, every column has a fixed data type, and some columns (like a primary key) must be unique and never blank — like a passport number field that can't be duplicated or empty.

Problem it solves

Without a defined structure, nothing stops inconsistent or invalid data from entering the system. Constraints at table-creation time push validation down to the database layer, as a last line of defense beneath your Java service layer.

create_table.sql
CREATE TABLE employees (
  id          INT AUTO_INCREMENT PRIMARY KEY,
  first_name  VARCHAR(50)  NOT NULL,
  email       VARCHAR(120) UNIQUE NOT NULL,
  salary      DECIMAL(10,2) DEFAULT 0.00,
  dept_id     INT,
  created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT fk_emp_dept
    FOREIGN KEY (dept_id) REFERENCES departments(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
→ Query OK, 0 rows affected
→ Table employees created with 1 primary key, 1 unique key, 1 foreign key
→ Storage engine: InnoDB (supports transactions + FK enforcement)

01ER-style blueprint

02Constraint types

PRIMARY KEY

Uniquely identifies each row. Implies NOT NULL + UNIQUE. Only one per table (can be composite).

FOREIGN KEY

Enforces referential integrity — value must exist in the referenced table's key column.

UNIQUE

No duplicate values, but unlike PK, allows one NULL (InnoDB allows multiple NULLs actually).

NOT NULL

Column must always have a value — the most common validation constraint.

DEFAULT

Auto-fills a value when none is supplied on INSERT.

CHECK (MySQL 8.0.16+)

Validates a boolean condition, e.g. CHECK (salary >= 0). Ignored silently before 8.0.16.

03How MySQL works internally

On CREATE TABLE, InnoDB allocates a tablespace (by default one .ibd file per table, controlled by innodb_file_per_table), writes table metadata to the data dictionary, builds a clustered index on the primary key (InnoDB physically stores rows in primary-key order), and registers any foreign keys for constraint checking on every DML.

Interview trap

"InnoDB stores data in the leaf nodes of the primary key's B+Tree — this is called a clustered index." If a table has no explicit primary key, InnoDB picks the first UNIQUE NOT NULL key, or silently creates a hidden 6-byte row ID.

05Spring Boot relation

In JPA/Hibernate, a @Entity class maps to a table created by this exact DDL shape. spring.jpa.hibernate.ddl-auto=update can auto-generate tables from entities in dev — but in production, teams almost always set it to validate or none and manage schema via versioned migration tools like Flyway or Liquibase instead.

Beginner mistake

Using ddl-auto=update in production. It can silently alter live tables in ways that don't match your intended migration history, and it never drops or renames columns safely.

06Interview questions

What is the difference between PRIMARY KEY and UNIQUE KEY?+

A table can have only one PRIMARY KEY but multiple UNIQUE keys. PRIMARY KEY never allows NULL; UNIQUE technically allows NULLs (InnoDB permits multiple NULLs since NULL ≠ NULL in comparison). PK also defines InnoDB's physical clustered storage order.

Can a table have a composite primary key?+

Yes — PRIMARY KEY (order_id, product_id) is common in junction/mapping tables representing many-to-many relationships.

Scenario: You need a temporary table just for a report that disappears after the session. What do you use? Scenario+

CREATE TEMPORARY TABLE — visible only to the current session/connection and automatically dropped when the session ends. Useful for staging intermediate report data without polluting the schema.

Asked at Zoho: What storage engine does MySQL use by default and why does it matter? Zoho+

InnoDB, default since MySQL 5.5. It matters because InnoDB supports transactions (ACID), row-level locking, and foreign keys — while the older MyISAM engine doesn't support transactions or FK constraints and uses table-level locking.

03 · Reference

Data Types

Picking the right type is a performance and correctness decision, not a formality — and it's one of the most common "gotcha" interview areas.

  • INT — 4 bytes, ~±2.1 billion. Standard choice for IDs and counts.
  • BIGINT — 8 bytes, used when INT could overflow (e.g. global row counters).
  • DECIMAL(p,s) — exact fixed-point. Always use for money.
  • FLOAT / DOUBLE — approximate, fast, but rounding errors make them unsafe for currency.
  • TINYINT(1) — commonly used to represent BOOLEAN (MySQL has no native boolean type).
  • CHAR(n) — fixed length, right-padded with spaces, faster for uniform-length data (e.g. country codes).
  • VARCHAR(n) — variable length, stores only what's needed + 1-2 length bytes. Default choice for names, emails.
  • TEXT / MEDIUMTEXT / LONGTEXT — for large text blocks (articles, descriptions) beyond VARCHAR's 65,535-byte row limit practicality.
  • ENUM — a fixed list of allowed string values, stored internally as integers for efficiency.
  • DATE — YYYY-MM-DD only.
  • DATETIME — date + time, range 1000–9999, timezone-independent, 8 bytes (5 in modern MySQL with fractional precision support).
  • TIMESTAMP — date + time, stored as UTC internally, range only 1970–2038, auto-converts on read per session timezone, can auto-update on row change with ON UPDATE CURRENT_TIMESTAMP.
  • YEAR — 1-byte year-only value.
  • JSON (5.7+) — validates and stores JSON documents natively, queryable with -> and ->> operators.
  • BLOB — binary large object for files/images (though storing files outside the DB is usually preferred).
  • SET — like ENUM but allows multiple selected values from a fixed list, stored as a bitmap.

Classic interview trap

"Why not use FLOAT for a price column?" — Answer: FLOAT/DOUBLE are binary approximations and can produce rounding errors like 0.1 + 0.2 ≠ 0.3. Always use DECIMAL(p,s) for currency, which stores exact digits.

Memory trick

"CHAR is a Chair — fixed size, doesn't stretch. VARCHAR VARies — grows to fit." DECIMAL = Dollar-safe. FLOAT = Fuzzy.

04 · Statement

ALTER TABLE

Renovating a live building without knocking it down — ALTER changes structure while (ideally) preserving existing data.

alter_table.sql
-- Add a column
ALTER TABLE employees ADD COLUMN phone VARCHAR(15);

-- Change type only (keeps name)
ALTER TABLE employees MODIFY COLUMN phone VARCHAR(20);

-- Rename AND retype (old syntax)
ALTER TABLE employees
  CHANGE COLUMN phone contact_number VARCHAR(20);

-- Rename only (MySQL 8+)
ALTER TABLE employees RENAME COLUMN contact_number TO phone;

-- Drop a column
ALTER TABLE employees DROP COLUMN phone;
→ 4 ALTER operations queued
→ MySQL 8: ADD COLUMN at end uses ALGORITHM=INSTANT (near-zero downtime)
→ MODIFY/CHANGE with type change may trigger a full table rebuild

01MODIFY vs CHANGE

AspectMODIFY COLUMNCHANGE COLUMN
Rename columnNoYes
Change data typeYesYes
Syntax needs old + new nameOnly current nameBoth old and new name
MySQL-specific?YesYes (non-standard SQL)

02How MySQL works internally

Historically, most ALTER operations rebuilt the entire table: copy all rows into a new tablespace with the new structure, then swap. Since MySQL 5.6+, Online DDL allows many operations (like adding a secondary index) to run with the table still readable/writable. MySQL 8.0 introduced Instant DDL (ALGORITHM=INSTANT) for operations like adding a nullable column at the end of a table — metadata-only change, no table rewrite, no long lock.

Performance note

On a multi-million-row table, an ALTER that forces a full rebuild (e.g. changing a column's data type) can lock the table for minutes and stall production traffic. Real teams use tools like gh-ost or pt-online-schema-change to perform the migration on a shadow table and cut over with minimal locking.

Beginner mistake

Running large ALTERs directly against production during peak hours without checking whether it's an instant, in-place, or full-table-copy operation (visible via ALTER TABLE ... ALGORITHM=INPLACE, LOCK=NONE hints or EXPLAIN-like tooling).

03Interview questions

How do you rename just a column without changing its type in MySQL 8?+

ALTER TABLE t RENAME COLUMN old_name TO new_name; — added in MySQL 8.0, cleaner than the older CHANGE COLUMN syntax which forced you to restate the type.

How do you add a column at a specific position?+

Use AFTER column_name, e.g. ALTER TABLE employees ADD COLUMN age INT AFTER first_name;. Without it, new columns append at the end. Note: positioned adds are not eligible for instant DDL.

Scenario: You need to add a NOT NULL column to a table with 50 million existing rows with zero downtime. What's your approach? Scenario+

Add the column as nullable first (instant in MySQL 8), backfill values in small batches, then add a NOT NULL constraint once every row has a value — or use an online schema-change tool to avoid long metadata locks on a live table.

DROP vs TRUNCATE vs DELETE

Security note

DROP and TRUNCATE both require elevated privileges (DROP privilege) and are irreversible in normal operation. Production databases typically restrict these privileges to DBAs/admin roles and require them to run through reviewed migration scripts, not ad-hoc connections.

drop_truncate.sql
TRUNCATE TABLE audit_logs;    -- resets AUTO_INCREMENT, keeps structure
DROP TABLE IF EXISTS audit_logs;  -- removes structure entirely
DELETE FROM audit_logs WHERE created_at < '2025-01-01';
→ TRUNCATE: table emptied, storage reallocated, id counter reset to 1
→ DROP: table + metadata removed permanently
→ DELETE: only matching rows removed, transaction-safe, triggers fired

01Interview questions

Why can't you rollback a TRUNCATE inside a transaction?+

TRUNCATE is DDL. DDL statements in MySQL implicitly commit any open transaction before and after execution, so there's nothing to roll back once it runs.

Asked at Infosys: A table referenced by a foreign key won't TRUNCATE — why, and how do you fix it? Infosys+

InnoDB blocks TRUNCATE on a parent table if a child table has an active foreign key referencing it, to protect referential integrity. Fix: temporarily SET FOREIGN_KEY_CHECKS=0;, truncate, then re-enable — or drop/recreate the FK, or truncate child tables first.

Scenario: You accidentally ran DELETE without WHERE on a 10M row table in a transaction that hasn't committed yet. Can you recover? Scenario+

Yes — since DELETE is DML, you can issue ROLLBACK; before COMMIT to undo it. This is exactly why DELETE, despite being slower, is the safer choice for destructive operations you might need to reverse.

06 · Statement

RENAME TABLE

A small statement with a surprisingly popular production trick: atomic, zero-downtime table swaps.

rename.sql
-- Simple rename
RENAME TABLE employees TO staff;
-- Equivalent
ALTER TABLE employees RENAME TO staff;

-- Atomic zero-downtime swap (classic production trick)
RENAME TABLE
  staff TO staff_old,
  staff_new TO staff;
→ RENAME TABLE is atomic even across multiple tables in one statement
→ No readers ever see a missing "staff" table during the swap

01Why the multi-table swap matters

If you were to DROP staff; RENAME staff_new TO staff; as two separate statements, there'd be a brief window where staff doesn't exist and live queries would fail. A single multi-table RENAME TABLE statement executes as one atomic operation, so the table is never momentarily missing — a technique used for zero-downtime schema migrations (build a shadow table, backfill it, then swap it in).

Interview tip

Mention this swap trick specifically — it signals production experience far beyond fresher-level tutorials.

07 · Standards

Naming Conventions

Not enforced by MySQL, but enforced by every code review. Interviewers use this to judge whether you'll write maintainable schema code on a real team.

Tables

lower_snake_case, usually plural: employees, order_items.

Columns

lower_snake_case, singular: first_name, created_at.

Primary keys

Simply id, or employee_id if you prefer explicit FK-matching names.

Foreign keys

<referenced_table_singular>_id, e.g. dept_id. Constraint name: fk_child_parent.

Indexes

idx_table_column, e.g. idx_employees_email.

Booleans

Prefix with is_ / has_: is_active, has_verified_email.

Case sensitivity gotcha

Table name case-sensitivity depends on the OS and the lower_case_table_names system variable — Linux MySQL is case-sensitive for table names by default, Windows/macOS often isn't. A team developing on Windows and deploying on Linux can hit "table not found" bugs purely from casing mismatches. Convention: always use lowercase.

01Spring Boot / JPA relation

Hibernate's default SpringPhysicalNamingStrategy automatically converts a Java camelCase field like firstName into the snake_case column first_name, and a class EmployeeRecord into table employee_record — so following snake_case convention in the database keeps your entities mapping cleanly without needing explicit @Column(name=...) overrides everywhere.

Memory trick

"Tables are Teams (plural), Columns are Characteristics (singular)." A table holds many rows, so name it plural; a column describes one attribute per row, so name it singular.

Cheat Sheet

Every syntax pattern from this module, in one scannable block.

cheatsheet.sql
-- Database
CREATE DATABASE IF NOT EXISTS db CHARACTER SET utf8mb4;
DROP DATABASE IF EXISTS db;
SHOW DATABASES; USE db;

-- Table
CREATE TABLE t (id INT AUTO_INCREMENT PRIMARY KEY, name VARCHAR(50) NOT NULL);
CREATE TABLE t2 LIKE t;          -- clone structure
CREATE TABLE t3 AS SELECT * FROM t;   -- clone data, no keys

-- Alter
ALTER TABLE t ADD COLUMN c INT;
ALTER TABLE t MODIFY COLUMN c BIGINT;
ALTER TABLE t CHANGE COLUMN c c2 BIGINT;
ALTER TABLE t RENAME COLUMN c2 TO c3;
ALTER TABLE t DROP COLUMN c3;

-- Drop / Truncate / Delete
DROP TABLE IF EXISTS t;
TRUNCATE TABLE t;
DELETE FROM t WHERE id = 1;

-- Rename
RENAME TABLE a TO a_old, a_new TO a;

Wrap-up

Summary & Revision Notes

Database = Schema

MySQL treats them as synonyms — a namespace holding tables.

CREATE TABLE

Defines columns, types, and constraints (PK, FK, UNIQUE, NOT NULL, DEFAULT, CHECK).

DECIMAL for money

Never FLOAT/DOUBLE — rounding errors break financial correctness.

ALTER is evolving, not destructive

ADD, MODIFY, CHANGE, RENAME COLUMN, DROP COLUMN — know when each applies.

DROP ≠ TRUNCATE ≠ DELETE

DDL vs DML, rollback capability, WHERE support, trigger firing — this table is asked everywhere.

RENAME TABLE is atomic

Multi-table swaps enable zero-downtime schema cutovers.

Naming conventions aren't optional

snake_case, plural tables, singular columns — Hibernate expects this by default.

Before your interview

Be ready to write CREATE TABLE with constraints on a whiteboard from memory, explain DROP vs TRUNCATE vs DELETE without hesitating, and justify VARCHAR vs CHAR and DECIMAL vs FLOAT with a one-line reason each.
