Normalization

Every module before this one assumed a well-designed schema. This is where you learn why that schema looks the way it does — the formal rules (1NF → BCNF) behind eliminating duplicate and inconsistent data, and when to deliberately break those rules.

⭐ Why this module is the capstone

Normalization is the "why" behind every earlier module

Modules 3 through 11 all assumed tables were already split sensibly with foreign keys connecting them. Normalization is the formal reasoning for why — and it's one of the few genuinely conceptual (not syntax) topics fresher interviews test deeply.

Problem it solves

Without normalization rules, a single table can store the same customer's phone number in a thousand rows. Update one, forget the other 999, and now your data is silently inconsistent — this is called an update anomaly.

Real-world analogy

An unnormalized table is like writing your address on every single letter in a filing cabinet instead of keeping one address book and referencing an ID. Normalization builds the address book.

01The three classic anomalies

Update anomaly

The same fact (e.g. a customer's phone) is duplicated in many rows — updating it in one place but not another leaves contradictory data.

Insert anomaly

You can't add a new product until someone orders it, because product info only exists embedded inside order rows.

Delete anomaly

Deleting the only order for a customer accidentally erases the only record of that customer ever existing.

01 · Normal Form

1NF — First Normal Form

The entry ticket: every column must hold a single, atomic value — no lists, no repeating groups of columns.

Violates 1NFFixed for 1NF
phones: "9876543210, 9123456780"One row per phone number in a separate phones table, or one phone per row
product1, product2, product3 columnsA separate order_items table, one row per product
before_1nf.sql
-- BEFORE (violates 1NF): repeating "product" columns
CREATE TABLE orders_bad (
  order_id INT PRIMARY KEY,
  customer_name VARCHAR(100),
  product1 VARCHAR(50),
  product2 VARCHAR(50)
);

-- AFTER (1NF): one row per order item, atomic values
CREATE TABLE order_items (
  order_id INT,
  product_name VARCHAR(50),
  PRIMARY KEY (order_id, product_name)
);
→ Any number of products per order is now possible without adding columns — the classic "productN" anti-pattern is eliminated
Beginner mistake

Storing comma-separated IDs in a single column (e.g. tag_ids: "3,7,12") to "save a table." This breaks 1NF, makes indexing/searching that column nearly impossible, and forces string-parsing logic into every query.

01Interview questions

What does "atomic value" mean in 1NF?+

A single, indivisible value per column/row cell — not a list, not a comma-separated string, not a nested structure (outside of an explicit JSON column used deliberately).

Scenario: A "skills" column stores "Java, Spring, MySQL" for each employee. Why is this a problem? Scenario+

It violates 1NF — you can't efficiently query "find employees who know MySQL" with an index, can't enforce a valid skill list, and updating one skill requires string manipulation. Fix: a separate employee_skills junction table.

02 · Normal Form

2NF — Second Normal Form

Must already be in 1NF, plus: every non-key column must depend on the whole composite primary key, not just part of it.

2NF only becomes relevant when a table has a composite primary key (two or more columns together). If your PK is a single column, your table is automatically in 2NF once it's in 1NF.

before_2nf.sql
-- BEFORE (violates 2NF): product_name depends only on product_id,
-- NOT on the full (order_id, product_id) composite key -- a partial dependency
CREATE TABLE order_items_bad (
  order_id INT,
  product_id INT,
  product_name VARCHAR(50),  -- depends only on product_id
  quantity INT,                -- depends on BOTH columns -- OK
  PRIMARY KEY (order_id, product_id)
);

-- AFTER (2NF): product_name moved to its own table, keyed by product_id alone
CREATE TABLE products (product_id INT PRIMARY KEY, product_name VARCHAR(50));
CREATE TABLE order_items (
  order_id INT, product_id INT, quantity INT,
  PRIMARY KEY (order_id, product_id)
);
→ product_name is now stored once per product, not once per order line — updating a product's name only touches one row
Interview framing

"Partial dependency" is the exact term to use: a non-key attribute depends on only part of a composite primary key rather than the whole thing.

01Interview questions

Why doesn't 2NF apply to tables with a single-column primary key?+

Partial dependency can only exist against part of a composite key. With a single-column PK, every non-key column depends on the entire key by definition, so 1NF + a single-column PK already satisfies 2NF.

03 · Normal Form

3NF — Third Normal Form

Must already be in 2NF, plus: no non-key column may depend on another non-key column — no transitive dependency.

before_3nf.sql
-- BEFORE (violates 3NF): dept_name depends on dept_id, not directly on employee_id
-- employee_id -> dept_id -> dept_name is a transitive dependency
CREATE TABLE employees_bad (
  employee_id INT PRIMARY KEY,
  dept_id INT,
  dept_name VARCHAR(50)  -- transitively dependent on dept_id, not employee_id
);

-- AFTER (3NF): dept_name lives only in departments
CREATE TABLE departments (dept_id INT PRIMARY KEY, dept_name VARCHAR(50));
CREATE TABLE employees (
  employee_id INT PRIMARY KEY,
  dept_id INT,
  FOREIGN KEY (dept_id) REFERENCES departments(dept_id)
);
→ Renaming a department now updates exactly one row, and can never disagree between two employees in the same department
Memory trick — the classic 3NF mnemonic

"The key, the whole key, and nothing but the key." 1NF+2NF get you "the key, the whole key"; 3NF adds "nothing but the key" — every non-key column depends directly on the primary key, and on nothing else.

01Interview questions

What is a transitive dependency, in plain terms?+

When column A determines column B, and column B determines column C, then C is transitively dependent on A (through B) rather than directly. 3NF requires removing such chains by moving C into its own table keyed by B.

Asked at HCL: Why is 3NF considered "good enough" for most production schemas? HCL+

3NF eliminates the vast majority of real-world update/insert/delete anomalies while remaining simple to reason about and query. Going further to BCNF or beyond is rare outside academic settings or schemas with unusual overlapping candidate keys.

04 · Normal Form

BCNF — Boyce-Codd Normal Form (basic)

A stricter version of 3NF for the rare case of overlapping candidate keys. Fresher interviews want the definition and a recognizable example — not a deep derivation.

The one-line definition to memorize

For every functional dependency A → B, A must be a candidate key (a "super key" minimal enough to uniquely identify a row). In other words: every determinant must be a candidate key.

01Classic textbook example

Consider a table tracking which instructor teaches which subject in which room, where each instructor teaches only one subject, but a room can host multiple subjects:

student_idsubjectinstructor
101DBMSProf. Rao
102DBMSProf. Rao
103JavaProf. Iyer

This is already in 3NF (no transitive dependency through a non-key column) — but instructor → subject holds too (each instructor teaches exactly one subject), and instructor is not a candidate key of this table. That's the BCNF violation: a determinant that isn't a candidate key.

bcnf_fix.sql
-- Split so the "instructor -> subject" dependency is captured in its own table
CREATE TABLE instructor_subject (
  instructor VARCHAR(50) PRIMARY KEY,
  subject VARCHAR(50)
);
CREATE TABLE enrollment (
  student_id INT,
  instructor VARCHAR(50),
  PRIMARY KEY (student_id, instructor),
  FOREIGN KEY (instructor) REFERENCES instructor_subject(instructor)
);
→ instructor → subject is now enforced by instructor being a PRIMARY KEY in its own table — the determinant IS a candidate key
Interview trap

BCNF is rarely the deciding factor in an interview — most interviewers just want to hear "every determinant must be a candidate key" and a simple example. Deep BCNF derivation is graduate/academic-level and almost never expected from freshers.

05 · Trade-off

Denormalization

Deliberately reintroducing redundancy to trade write-complexity for read-speed — a controlled, documented decision, not a mistake.

AspectNormalizedDenormalized
Data redundancyMinimalIntentional duplication
Write complexitySimple, single-row updatesMust update duplicated copies consistently
Read performanceMay need multiple JOINsOften a single-table read — faster
Typical use caseTransactional (OLTP) systemsReporting/analytics (OLAP), caching, read-heavy dashboards
RiskSlower complex readsData inconsistency if updates are missed
denormalize_example.sql
-- Normalized: order total must be computed via JOIN + SUM every time
SELECT o.id, SUM(oi.price * oi.qty)
FROM orders o JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id;

-- Denormalized: pre-computed total_amount column, updated whenever items change
ALTER TABLE orders ADD COLUMN total_amount DECIMAL(10,2);
SELECT id, total_amount FROM orders; -- instant read, no JOIN
→ Dashboard reads become a single-table SELECT instead of a JOIN + SUM — at the cost of keeping total_amount in sync on every order_items change
Best practice

Denormalize deliberately and narrowly — a cached total, a materialized reporting table, a read-replica with a flattened view — while keeping the normalized tables as the source of truth. Never denormalize your entire OLTP schema "for speed" without measuring first.

Beginner mistake

Denormalizing prematurely, before profiling actually shows a JOIN is a bottleneck — this trades away data integrity for a performance problem that may not even exist yet.

01Interview questions

When would you choose to denormalize a schema?+

When read performance on a well-indexed, properly normalized JOIN is genuinely proven to be a bottleneck (via profiling/EXPLAIN), and the redundant data can be reliably kept in sync — commonly for reporting dashboards, caching layers, or search-optimized read models.

06 · Applied

Real-world Design

How normalization theory actually plays out designing a schema from scratch — the exercise interviewers love to run live on a whiteboard.

01Worked example: designing an e-commerce schema

Customers place orders. Each order contains multiple products, each with its own quantity and price at time of purchase. Products belong to categories. Customers can have multiple saved addresses.

  • customers — one row per customer
  • addresses — many per customer (1-to-many)
  • categories — one row per product category
  • products — belongs to one category
  • orders — belongs to one customer, ships to one address
  • order_items — junction table between orders and products (many-to-many), storing quantity and price_at_purchase
CREATE TABLE customers (id INT PRIMARY KEY AUTO_INCREMENT, name VARCHAR(100));
CREATE TABLE addresses (id INT PRIMARY KEY AUTO_INCREMENT, customer_id INT, line1 VARCHAR(200));
CREATE TABLE categories (id INT PRIMARY KEY AUTO_INCREMENT, name VARCHAR(50));
CREATE TABLE products (id INT PRIMARY KEY AUTO_INCREMENT, category_id INT, name VARCHAR(100), price DECIMAL(10,2));
CREATE TABLE orders (id INT PRIMARY KEY AUTO_INCREMENT, customer_id INT, address_id INT, order_date TIMESTAMP);
CREATE TABLE order_items (
  order_id INT, product_id INT,
  quantity INT, price_at_purchase DECIMAL(10,2),
  PRIMARY KEY (order_id, product_id)
);
Interview trap

Why store price_at_purchase in order_items instead of just joining to products.price? Because product prices change over time — an order must preserve the price at the moment of purchase, even after the product's current price changes. This is a deliberate, justified duplication, not a normalization mistake.

02Interview questions

Asked at Zoho: Design a database schema for a food delivery app. Walk through your normalization decisions. Zoho+

Identify entities (users, restaurants, menu_items, orders, order_items, delivery_addresses), separate repeating groups into junction tables (order_items for many-to-many between orders and menu_items), and deliberately snapshot price at order time — exactly the same reasoning as the e-commerce example above.

Scenario: Your team wants to add a denormalized "customer_full_name" column to the orders table to avoid a JOIN. What do you push back on? Scenario+

Ask if this is solving a proven performance problem (has JOIN actually been profiled as slow?) versus a premature optimization. If it proceeds, insist on a clear, documented sync strategy (trigger, application-level update, or scheduled job) so the duplicated name never silently diverges from the source of truth in customers.

Cheat Sheet

1NF

Atomic values only. No repeating groups, no comma-separated lists in one column.

2NF

1NF + no partial dependency on part of a composite primary key.

3NF

2NF + no transitive dependency — non-key columns depend only on the key.

BCNF

3NF + every determinant (A in A→B) must itself be a candidate key.

Denormalization

Deliberate, measured redundancy for read performance — never a default.

Real-world design

Identify entities → find repeating groups → extract junction tables → decide what to intentionally snapshot/duplicate.
