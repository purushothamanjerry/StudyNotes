01

Introduction

Before touching PostgreSQL internals (MVCC, WAL, indexes — covered in later modules), an interviewer first checks one thing: can you write and reason about plain SQL confidently. This module rebuilds that foundation with a PostgreSQL lens.

Real-world analogy

Think of a database table as a spreadsheet inside a filing cabinet. SELECT is "show me rows," WHERE is "only rows matching this filter," JOIN is "combine two spreadsheets using a shared column," and constraints are the office rules that stop someone typing garbage into a cell.

Same core SQL

SELECT, INSERT, UPDATE, DELETE, WHERE, GROUP BY, ORDER BY, JOIN, and constraints work almost identically to MySQL.

PostgreSQL extras

RETURNING, ON CONFLICT (upsert), array & JSONB operators, window functions, and CTEs go beyond standard MySQL syntax.

What interviewers test

Not syntax memorisation — they test execution order, NULL handling, join correctness, and constraint reasoning.

02

Why This Topic Exists & The Problem It Solves

Every Java backend eventually talks to a relational store. SQL is the contract between your Spring Boot service and the data. Get it wrong and you get slow endpoints, wrong reports, or corrupted data — the exact things interviewers probe for.

PROBLEMRaw data sits in tables, unordered, unfiltered
SQLDeclarative language to ask questions of data
ENGINEPostgres planner decides how to answer
RESULTExact rows your REST API needs

WHY POSTGRESQL EXISTS ALONGSIDE MYSQL

MySQL optimised historically for simple, fast reads at web scale. PostgreSQL optimised for correctness, extensibility, and standards compliance — richer types, better constraint enforcement, and a more powerful query planner for complex analytical SQL. That's why fintech, SaaS, and data-heavy product companies lean Postgres.

03

SELECT — Reading Data

SELECT is the most common clause you'll write, and the one interviewers use to test if you understand logical execution order.

SELECT just means "show me these columns from this table." SELECT name, price FROM products; reads: give me the name and price column from the products table.
SELECT is a projection operation over a relation. PostgreSQL's planner rewrites your SELECT into an execution plan (Seq Scan / Index Scan → Filter → Sort → Limit) chosen by cost estimation, not by the order you typed the clauses.
Interviewers love asking: "What is the logical execution order of a SELECT query?" Answer: FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT/OFFSET. Note SELECT runs after WHERE and GROUP BY — that's why you can't use a column alias in WHERE.
SELECT id, name, price
FROM products
WHERE price > 100
ORDER BY price DESC
LIMIT 10;

Remember execution order with: "Father Went Grocery Hopping Sunday Ordering Lunch" → FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT.

04

WHERE — Filtering Rows

WHERE filters raw rows before any grouping happens. It cannot reference aggregate functions — that's what HAVING is for.

SELECT * FROM employees
WHERE department = 'Engineering' AND salary > 60000;

-- PostgreSQL-specific filter operators
SELECT * FROM users WHERE email ILIKE '%gmail.com'; -- case-insensitive LIKE
SELECT * FROM orders WHERE status = ANY(ARRAY['NEW','PACKED']);

NULL handling

WHERE column = NULL never matches anything — always use IS NULL / IS NOT NULL. This is a top asked trick question.

ILIKE is Postgres-only

MySQL's LIKE is case-insensitive by default (with default collation); Postgres LIKE is case-sensitive, so Postgres added ILIKE.

05

GROUP BY & HAVING

GROUP BY collapses rows sharing a value into a single summary row. HAVING then filters those summary rows using aggregate conditions.

RAW ROWS1000 orders
GROUP BYcollapse by customer_id
AGGREGATESUM(amount) per group
HAVINGkeep totals > 10000
SELECT customer_id, SUM(amount) AS total_spent
FROM orders
GROUP BY customer_id
HAVING SUM(amount) > 10000
ORDER BY total_spent DESC;

COMMON MISTAKE

Putting a filter that doesn't need aggregation inside HAVING instead of WHERE. Always filter raw rows with WHERE first (cheaper) — use HAVING only for aggregate conditions.

06

ORDER BY & LIMIT / OFFSET

ORDER BY sorts the final result set. LIMIT/OFFSET is PostgreSQL's pagination syntax — different keyword from MySQL's identical LIMIT but different from SQL Server's TOP/FETCH.

SELECT id, name
FROM products
ORDER BY created_at DESC
LIMIT 20 OFFSET 40; -- page 3, 20 per page

PERFORMANCE NOTE

Large OFFSET values are slow — Postgres still scans and discards skipped rows. For deep pagination, prefer keyset pagination: WHERE id < :lastSeenId ORDER BY id DESC LIMIT 20.

07

INSERT · UPDATE · DELETE

The three data-modification statements. PostgreSQL adds a very interview-relevant superpower: the RETURNING clause.

INSERT

INSERT INTO users (name, email)
VALUES ('Ravi', 'ravi@x.com')
RETURNING id;

RETURNING gives back the generated id in one round-trip — no separate SELECT needed. Huge for Spring Boot JPA/JDBC efficiency.

UPDATE

UPDATE orders
SET status = 'SHIPPED'
WHERE id = 101
RETURNING status;

Always pair UPDATE with a WHERE clause — omitting it updates every row in the table.

DELETE

DELETE FROM sessions
WHERE expires_at < NOW();

DELETE removes rows one at a time and fires triggers; TRUNCATE is faster but skips row-level triggers and resets identity.

POSTGRESQL-ONLY: UPSERT

INSERT INTO inventory (sku, qty)
VALUES ('SKU1', 5)
ON CONFLICT (sku)
DO UPDATE SET qty = inventory.qty + EXCLUDED.qty;

MySQL's equivalent is ON DUPLICATE KEY UPDATE — different syntax, same idea. This comparison is a favourite interview question.

08

Joins

Joins combine rows from two or more tables using a related column. Identical concept and syntax to MySQL.

INNER JOIN — only matching rows+
SELECT o.id, c.name
FROM orders o
INNER JOIN customers c ON o.customer_id = c.id;
Returns only orders that have a matching customer. If a customer has no orders, they're excluded entirely.
LEFT JOIN — all left rows + matches+
SELECT c.name, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id;
Returns every customer, even those with zero orders — unmatched columns come back as NULL. Classic "find customers with no orders" pattern: add WHERE o.id IS NULL.
RIGHT JOIN & FULL OUTER JOIN+
RIGHT JOIN is the mirror of LEFT JOIN (rarely used — usually rewritten as LEFT JOIN by swapping table order). FULL OUTER JOIN returns all rows from both sides, matched where possible, NULL where not.
SELF JOIN+
SELECT e.name, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;
A table joined to itself — used for hierarchical data like employee/manager trees.
TABLE Aorders (5 rows)
JOIN KEYcustomer_id = id
TABLE Bcustomers (3 rows)
RESULTmatched combined rows
09

Subqueries

A query nested inside another. PostgreSQL also lets you write the same logic more readably using a CTE (WITH), which is preferred in interviews for clarity.

Scalar / IN subquery

SELECT name FROM customers
WHERE id IN (
  SELECT customer_id FROM orders
  WHERE amount > 5000
);

Correlated subquery

SELECT name FROM employees e
WHERE salary > (
  SELECT AVG(salary) FROM employees
  WHERE department = e.department
);

Rewriting the first example as a CTE (readable, and reusable across the query):

WITH big_spenders AS (
  SELECT customer_id FROM orders WHERE amount > 5000
)
SELECT name FROM customers
WHERE id IN (SELECT customer_id FROM big_spenders);

COMMON MISTAKE

Correlated subqueries re-run once per outer row — fine for small tables, a performance trap on large ones. Interviewers expect you to mention this trade-off.

10

Constraints

Constraints are rules the database enforces automatically, so bad data never gets persisted — even if your Java code has a bug.

PRIMARY KEY

Unique + NOT NULL, one per table. Uniquely identifies each row.

FOREIGN KEY

Enforces that a column's value must exist in another table's referenced column — this is referential integrity.

UNIQUE

No two rows can share the same value in that column (NULLs are treated as distinct by default in Postgres).

NOT NULL

Column must always have a value — the single most common constraint interviewers ask about.

CHECK

Custom boolean rule, e.g. CHECK (price > 0) — rejects rows that fail it.

DEFAULT

Auto-fills a value (e.g. created_at TIMESTAMP DEFAULT NOW()) when none is provided.

CREATE TABLE orders (
  id SERIAL PRIMARY KEY,
  customer_id INT REFERENCES customers(id),
  amount NUMERIC CHECK (amount > 0),
  status VARCHAR(20) NOT NULL DEFAULT 'NEW'
);

Spring Boot Integration

As a Java Full Stack fresher, you'll mostly touch SQL through Spring Data JPA or JdbcTemplate — know how these clauses map.

JPA derived query

// Java — Spring Data JPA
List<Order> findByStatusAndAmountGreaterThan(
    String status, BigDecimal amount);
-- generates roughly:
SELECT * FROM orders
WHERE status = ? AND amount > ?;

@Query + native RETURNING

@Modifying
@Query(value = "UPDATE orders SET status=:s " +
  "WHERE id=:id RETURNING id", nativeQuery = true)

Native queries let you use Postgres-only features like RETURNING and ON CONFLICT that plain JPQL doesn't support.

Beginner Mistakes & Best Practices

MISTAKES

  • Using SELECT * in production code
  • Forgetting WHERE on UPDATE/DELETE
  • Comparing NULL with = instead of IS NULL
  • Not indexing foreign key columns used in JOINs
  • Mixing aggregate & non-aggregate columns without GROUP BY

BEST PRACTICES

  • Name columns explicitly instead of SELECT *
  • Wrap multi-statement DML in a transaction
  • Use RETURNING to avoid an extra round-trip
  • Prefer CTEs over deeply nested subqueries for readability
  • Always test edge cases: empty table, NULL values, duplicate keys

Interview Question Bank

Common, scenario-based, and product-company questions. Click a question to reveal the expected answer.

CommonScenario-basedProduct company
Q.What is the difference between WHERE and HAVING?
WHERE filters individual rows before grouping; HAVING filters grouped/aggregated results after GROUP BY. WHERE cannot use aggregate functions like SUM() or COUNT(); HAVING can.
Q.Why does WHERE run before SELECT logically, even though SELECT is written first?
SQL is declarative — the written order is not the execution order. Logical order is FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. That's why a column alias defined in SELECT can't be used in WHERE, but can be used in ORDER BY.
Q.Difference between INNER JOIN and LEFT JOIN?
INNER JOIN returns only rows with matches on both sides. LEFT JOIN returns all rows from the left table, filling unmatched right-side columns with NULL.
Q.You have 1M orders and need customers who never placed an order. How would you write it, and would you use NOT IN or LEFT JOIN?
Prefer LEFT JOIN ... WHERE o.id IS NULL over NOT IN (subquery). NOT IN breaks silently and returns zero rows if the subquery contains even one NULL — a classic Postgres/SQL trap. LEFT JOIN + IS NULL is both correct and typically better optimised.
Q.How would you implement "insert or update stock quantity" without a race condition?
Use PostgreSQL's atomic upsert: INSERT ... ON CONFLICT (sku) DO UPDATE SET qty = inventory.qty + EXCLUDED.qty. This is a single atomic statement, avoiding the classic check-then-update race condition of SELECT + IF EXISTS + UPDATE/INSERT in application code.
Q.A junior dev wrote DELETE FROM orders; and wiped the table. How do constraints/practices prevent this?
Always require WHERE in review/tooling, run destructive DML inside a transaction you can ROLLBACK, use a staging query (SELECT COUNT(*) with the same WHERE) before executing DELETE, and restrict production DB roles so ad-hoc DELETE isn't possible without review.
Q.What does the RETURNING clause do, and why is it useful in Spring Boot apps?
RETURNING gives back column values (like a generated id) from an INSERT/UPDATE/DELETE in the same round-trip, avoiding a second SELECT. In JDBC/JPA, this reduces one network call per write.
Q.Difference between UNIQUE constraint and PRIMARY KEY?
A table can have only one PRIMARY KEY, and it disallows NULLs. A table can have multiple UNIQUE constraints, and by default Postgres treats multiple NULLs in a UNIQUE column as distinct (not violating uniqueness).
Q.What's the difference between a correlated and non-correlated subquery?
A non-correlated subquery runs once, independent of the outer query. A correlated subquery references a column from the outer query and re-executes once per outer row — more expressive, but potentially much slower on large tables.

Summary & Key Takeaways

Core SQL (SELECT, WHERE, GROUP BY, JOIN, DML) is nearly identical between PostgreSQL and MySQL — your existing SQL knowledge transfers directly.
Logical execution order (FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT) is the #1 concept interviewers probe.
PostgreSQL-only syntax to remember: RETURNING, ON CONFLICT (upsert), ILIKE, and richer constraint defaults.
Constraints (PK, FK, UNIQUE, CHECK, NOT NULL) are your first line of data-integrity defense — mention them proactively in system design answers.
Prefer LEFT JOIN + IS NULL over NOT IN subqueries — the NULL trap is a very common interview gotcha.
