01What is PostgreSQL?

The single most common opening question in a database round. Answer it in layers — simple, technical, then interview-polished — and you're already ahead of most freshers.

Simple

PostgreSQL is a program that stores your data — like user records, orders, products — safely in tables, and lets you ask questions about that data using SQL.

Technical

PostgreSQL is an open-source object-relational database management system (ORDBMS) that implements the SQL standard while extending it with objects, custom types, inheritance, JSON support, and full ACID-compliant transactions.

Interview-Ready

"PostgreSQL is an open-source, ACID-compliant, object-relational database known for standards compliance, extensibility, and strong support for complex queries and concurrent transactions — commonly used as the primary datastore behind Spring Boot backends."

Analogy

Think of PostgreSQL as a highly disciplined librarian: every book (row) has a strict place (table/schema), every checkout is logged so nothing is ever lost mid-transaction, and the librarian can also handle very unusual requests (JSON documents, custom data types) without breaking the filing system.

Problem It Solves

Flat files & spreadsheets don't scale

Before RDBMSs, applications stored data in flat files — no relationships, no concurrency control, no guarantee that two users editing the same record wouldn't corrupt it. PostgreSQL solves this with structured tables, relationships (foreign keys), and transactional guarantees.

Real-World Example

An e-commerce order system

When you place an order: stock must decrease, payment must be recorded, and an order row must be created — all or nothing. PostgreSQL's transaction engine guarantees this even if the server crashes mid-request.

💡
Interview Tip

Interviewers love hearing "ORDBMS" instead of just "RDBMS" for Postgres — it signals you know Postgres supports object-oriented features (custom types, table inheritance) beyond plain relational databases like classic MySQL.

02History (short version — don't over-invest here)

You won't be quizzed deeply on history, but knowing the one-line origin story shows genuine familiarity.

1986

Started at UC Berkeley as the POSTGRES project by Michael Stonebraker, successor to the earlier "Ingres" database.

1996

Renamed to PostgreSQL after SQL support was added, reflecting its evolution into a full SQL-compliant system.

Ongoing

Maintained by a global open-source community (not a single company) — a point often raised to contrast with vendor-owned databases.

🧠
Memory Trick

"POSTGRES → Post-Ingres." It's literally the database that came after Ingres — that's the whole naming story in one word.

03Why Companies Use PostgreSQL

A very common follow-up to "what is PostgreSQL" is "why would we choose it?" — have concrete reasons ready.

Advantage

Standards Compliance

Closely follows ANSI SQL, reducing surprises when migrating between systems or hiring SQL-literate engineers.

Advantage

Extensibility

Custom data types, operators, and extensions (like PostGIS for geodata) without forking the database.

Advantage

Strong Concurrency (MVCC)

Multi-Version Concurrency Control lets readers and writers work simultaneously without blocking each other.

Advantage

JSON + Relational

Native JSONB support means teams get document-store flexibility without adding a separate NoSQL database.

Advantage

No Licensing Cost

Fully open-source (PostgreSQL License, a permissive license), removing vendor lock-in risk that comes with Oracle or SQL Server.

Advantage

Reliability

Write-Ahead Logging (WAL) and strict ACID guarantees make it a trusted choice for financial and transactional systems.

✅
Best Practice — Answering This

Name 3 reasons max in an interview, tied to a real scenario: "For a fintech backend, I'd pick PostgreSQL for its strict ACID guarantees and MVCC-based concurrency" lands better than reciting a feature list.

04PostgreSQL Architecture (Basic)

You won't be asked to draw this from memory as a fresher, but understanding the flow of a query makes every later module (indexes, transactions, locks) click faster.

Step-by-step

1) Your app opens a connection → 2) the Postmaster process forks a dedicated backend process for it → 3) that process parses and plans your SQL → 4) data is read from shared buffers (memory) or disk → 5) any write is first recorded in the WAL for crash safety, then applied.

Interview Line

"PostgreSQL uses a process-per-connection model — unlike thread-per-connection engines — and guarantees durability through Write-Ahead Logging before a transaction is considered committed."

⚠️
Common Mistake

Saying PostgreSQL is "multi-threaded per connection." It's actually process-based — each client connection gets its own OS process, which is why connection pooling (e.g., PgBouncer) matters for high-concurrency apps.

05PostgreSQL vs MySQL (Overview)

Since you already know MySQL, frame every answer as a contrast — interviewers specifically want to see you can compare, not just recall.

AspectPostgreSQLMySQL
TypeObject-Relational (ORDBMS)Purely Relational (RDBMS)
SQL ComplianceVery close to ANSI SQL standardHistorically more relaxed, has diverged in places
Concurrency ModelMVCC across all storageDepends on storage engine (InnoDB uses MVCC)
JSON SupportNative JSONB — indexed, queryableJSON type exists but less mature indexing
ExtensibilityCustom types, operators, extensions (PostGIS)Limited extensibility
ReplicationStrong, but historically more manual setupSimpler out-of-the-box replication
Read-heavy simple appsSlightly more overhead per connectionTraditionally faster for simple read-heavy workloads
Best FitComplex queries, analytics, data integrity-critical appsSimple, high-speed read/write web apps
When To Use PostgreSQL

Financial systems, apps needing complex joins/window functions, geospatial data, or a mix of relational + JSON data.

When NOT To Use PostgreSQL

Extremely simple, high-throughput read workloads with no complex relationships, where operational simplicity outweighs feature depth.

💡
Interview Tip

Never say "PostgreSQL is just better." Say: "It depends on the workload — PostgreSQL wins on data integrity and complex querying, MySQL wins on simplicity for straightforward CRUD-heavy apps."

07Database, Schema, Table

A classic fresher trap: candidates confuse "schema" with "database." Get this hierarchy airtight.

Simple

Database = the whole building. Schema = a floor/department inside it. Table = a filing cabinet on that floor holding actual rows of data.

Interview-Ready

"A database is the top-level container and connections are scoped to exactly one database. A schema is a logical namespace inside that database used to group and isolate tables — by default, everything lives in the 'public' schema unless organized otherwise."

CREATE DATABASE app_db;
\c app_db

CREATE SCHEMA audit;

CREATE TABLE public.users (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100) NOT NULL
);

CREATE TABLE audit.login_history (
  id SERIAL PRIMARY KEY,
  user_id INT REFERENCES public.users(id),
  logged_in_at TIMESTAMP DEFAULT now()
);
⚠️
Common Mistake

Calling "public" a database. It's a schema — the default one PostgreSQL creates automatically inside every new database.

✅
Best Practice

Use separate schemas (not separate databases) to isolate modules like audit, reporting, or per-tenant data — cross-schema joins are cheap; cross-database joins are not directly possible in PostgreSQL.

08Data Types

Expect a rapid-fire round: "what type would you use for X?" Know the categories, not just the names.

CategoryTypesUse Case
NumericSMALLINT, INTEGER, BIGINT, NUMERIC, REAL, DOUBLE PRECISIONIDs, counts, money (use NUMERIC for currency — never REAL)
CharacterCHAR(n), VARCHAR(n), TEXTNames, descriptions; TEXT for unbounded content
BooleanBOOLEANFlags like is_active, is_deleted
Date/TimeDATE, TIME, TIMESTAMP, TIMESTAMPTZ, INTERVALAlways prefer TIMESTAMPTZ for anything user-facing across timezones
JSONJSON, JSONBSemi-structured data; JSONB is binary & indexable — almost always the right pick
UUIDUUIDGlobally unique identifiers, common in distributed systems
ArrayINTEGER[], TEXT[]PostgreSQL-specific — store lists directly in a column
SpecialSERIAL / BIGSERIALAuto-incrementing integer (sugar over sequence + default)
Performance Note

VARCHAR(n) vs TEXT

In PostgreSQL, there's virtually no performance difference — both are stored the same way internally. Use VARCHAR(n) only when you need a hard length constraint; otherwise TEXT is idiomatic.

Performance Note

JSON vs JSONB

Always prefer JSONB unless you need to preserve exact input formatting/whitespace — JSONB is stored in binary, is faster to query, and supports GIN indexing.

⚠️
Common Mistake

Using FLOAT/REAL for money. Floating-point types lose precision — always use NUMERIC(p,s) for currency and financial calculations.

🧠
Memory Trick

"JSONB = J-Speed-B." B for Binary, B for Better performance, B for the type you should default to.

10Scenario-Based Questions

These test judgment, not memorization — structure your answer as: constraint → reasoning → decision.

Your team is deciding between one shared "public" schema vs. one schema per client (multi-tenant). What do you check first?
+
Model Answer
Expected client count and isolation needs — a handful of large clients benefits from per-schema isolation (easy backup/restore per tenant), while thousands of small tenants makes per-schema unmanageable and a shared schema with a `tenant_id` column is more practical.
A junior dev stored prices as FLOAT and totals are now slightly off in production. What happened and how do you fix it?
+
Model Answer
Floating-point types can't represent all decimal fractions exactly, causing rounding drift over many operations. Fix: migrate the column to NUMERIC(p,s), recompute existing aggregates, and add a review step to catch numeric-type choices in code review.
You're modeling a product's "attributes" that vary wildly between product categories (shoes have sizes, books have ISBNs). How do you design this?
+
Model Answer
Use a JSONB column for the variable attributes alongside fixed relational columns for the common fields (name, price, category). This avoids an unmanageable sparse table with hundreds of nullable columns, while keeping core fields queryable and indexed normally.

13Performance & Security Notes

Performance

Connections are expensive

Because each connection is a process, opening/closing connections frequently is costly — use a connection pool (HikariCP in Spring Boot, or PgBouncer at the DB layer).

Security

Least-privilege roles

Avoid connecting your app with the superuser role. Create a dedicated role with only the privileges the application actually needs (SELECT/INSERT/UPDATE on specific schemas).

14Spring Boot Relation

This is where interviewers connect the dots — expect this exact linkage to come up.

# application.properties
spring.datasource.url=jdbc:postgresql://localhost:5432/app_db
spring.datasource.username=app_user
spring.datasource.password=****
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.properties.hibernate.dialect=org.hibernate.dialect.PostgreSQLDialect
💡
Interview Tip

Mention that Spring Data JPA + Hibernate translates your @Entity classes into PostgreSQL DDL, and that connection pooling (HikariCP, Spring Boot's default) is what keeps process-based PostgreSQL connections efficient under load.

+
Solution
CREATE DATABASE shop_db;
\c shop_db
CREATE SCHEMA inventory;
CREATE TABLE inventory.items (

);
2. Add a JSONB column `metadata` to `items` and insert a row with a nested attribute.
+
Solution
ALTER TABLE inventory.items ADD COLUMN metadata JSONB;

INSERT INTO inventory.items (name, price, metadata)
VALUES ('Running Shoe', 59.99, '{"size": 9, "color": "black"}');

21Summary & Revision Notes

In One Paragraph

PostgreSQL is an open-source, ACID-compliant object-relational database that stores data across a Database → Schema → Table hierarchy, uses process-based connections with WAL for durability and MVCC for concurrency, and offers rich data types (especially JSONB) that make it a strong default choice for Java Spring Boot backends where data integrity matters.

Revision Checklist

✔ Define PostgreSQL in 3 styles (simple/technical/interview)
✔ Explain the query flow (client → postmaster → backend → WAL/buffers)
✔ Contrast with MySQL confidently
✔ Get DB/Schema/Table hierarchy right every time
✔ Know when to use NUMERIC, JSONB, TIMESTAMPTZ, UUID
