PostgreSQL Internals — what actually happens under the hood.

The six internals concepts that separate a fresher who memorized syntax from one who understands how PostgreSQL guarantees durability, handles concurrency, and stays fast: WAL, MVCC, the Query Planner, Indexes, Vacuum, and Autovacuum — explained at exactly the depth product-company interviews expect from a fresher.

Introduction

00Why Internals Matter

Anyone can write a SELECT statement. Interviewers use internals questions specifically to separate candidates who copy-pasted SQL tutorials from candidates who understand what the database is actually doing.

Problem It Solves

"It works on my machine, but slow in production"

Without understanding indexes, vacuum, or the planner, a fresher can write correct SQL that becomes unusably slow at real data volume — and won't know why, or how to fix it.

Real-World Example

A "dead tuple" pileup

An app does frequent UPDATEs on a `users` table. Over weeks, the table balloons in size and queries slow down — the actual cause is that old row versions (dead tuples) were never cleaned up because autovacuum was misconfigured.

💡
Interview Tip

When an interviewer asks "how would you debug a slow query," internals vocabulary (planner, index scan, vacuum) is what makes your answer sound senior, not just correct.

DurabilityVery Frequently Asked

01WAL — Write-Ahead Logging

The single mechanism behind PostgreSQL's crash-safety guarantee.

Simple

Before PostgreSQL changes anything on disk, it first writes down "what I'm about to do" in a log. If the power goes out mid-change, it can replay the log on restart and finish the job correctly.

Technical

Every modification is first recorded as a WAL record in sequential log files before the corresponding data page is modified in shared buffers. A transaction is considered durable only once its WAL record is flushed to disk (fsync).

Interview-Ready

"WAL guarantees durability — the 'D' in ACID — by ensuring no committed transaction can be lost even if the server crashes right after commit, because the change is already safely logged before it's applied to the actual data files."

Analogy

Like a construction crew that writes down the blueprint change order and files it in a fireproof cabinet before touching the building — if a fire happens mid-renovation, the order survives and the work can be redone correctly.

The key insight: the WAL write in step 1 happens before the data page write in step 2 — that ordering is the entire mechanism.
⚠️
Common Mistake

Saying "WAL improves performance." Its primary purpose is durability/crash recovery — any performance benefit (like using it for replication) is secondary.

✅
Best Practice / Real Use

Streaming replication and point-in-time recovery both work by shipping WAL records to replicas — so understanding WAL also explains how PostgreSQL replication works underneath.

ConcurrencyVery Frequently Asked

02MVCC — Multi-Version Concurrency Control

The mechanism that lets readers and writers work at the same time without blocking each other.

Simple

Instead of locking a row while someone reads it, PostgreSQL keeps multiple "snapshots" (versions) of that row. A reader sees the version that existed when their query started, even if someone else is updating it right now.

Technical

Every row (tuple) has hidden `xmin`/`xmax` system columns marking the transaction IDs that created and deleted it. An UPDATE doesn't overwrite a row in place — it inserts a new tuple version and marks the old one as expired (a "dead tuple"), which vacuum later reclaims.

Interview-Ready

"MVCC means readers never block writers and writers never block readers — each transaction sees a consistent snapshot of the data based on transaction visibility rules, not on locking the whole row."

Analogy

Like Google Docs version history — editing the doc doesn't erase the version someone else is currently viewing; they keep seeing their snapshot until they refresh.

The old row (xmax=42) becomes a dead tuple — invisible to new transactions but not yet physically removed. That's exactly what Vacuum cleans up.
⚠️
Common Mistake

Thinking MVCC means "no locks are ever used." Locks still exist for write-write conflicts (two transactions updating the same row) — MVCC specifically removes the need for read locks.

🧠
Memory Trick

"MVCC = Many Versions, Calm Concurrency." Multiple row versions is exactly what keeps readers and writers calm around each other.

Optimizer

03Query Planner

Decides how your SQL actually gets executed — this is why the same query can be fast or slow depending on the data.

Simple

You tell PostgreSQL what you want (SQL); the planner decides how to get it fastest — like a GPS choosing the best route, not just knowing the destination.

Technical

The planner is cost-based: it estimates the cost of multiple possible execution plans (sequential scan vs index scan, join orders and algorithms) using table statistics gathered by ANALYZE, then picks the cheapest estimated plan.

Interview-Ready

"PostgreSQL uses a cost-based optimizer. It relies on table statistics — row counts, value distribution — to estimate the cost of different plans, which is why stale statistics after a bulk insert can lead to a bad plan until ANALYZE runs."

EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 42;

-- Sample output:
-- Index Scan using idx_customer_id on orders
--   (cost=0.29..8.31 rows=5 width=64) (actual time=0.02..0.03 rows=5)
Step-by-step Flow

Parse → Plan → Execute

1) Parser checks SQL syntax → 2) Planner generates candidate plans and picks the cheapest using statistics → 3) Executor runs the chosen plan and streams results back.

Interview Tool

EXPLAIN ANALYZE

Shows the actual plan chosen, estimated vs actual row counts, and time per step — the #1 tool interviewers expect you to know for debugging slow queries.

⚠️
Common Mistake

Assuming an index is always used just because it exists. If the table is small, or the query returns most of the rows, the planner may correctly choose a sequential scan instead — that's not a bug.

PerformanceVery Frequently Asked

04Indexes

The single most common performance-tuning topic in interviews.

Simple

An index is like a book's index page — instead of reading every page (row) to find a topic, you jump straight to the right page number.

Technical

By default PostgreSQL creates a B-tree index, a balanced tree structure that lets lookups, range scans, and sorts happen in O(log n) instead of scanning every row (O(n)).

Interview-Ready

"An index trades write speed and storage for read speed — every INSERT/UPDATE now also has to update the index, so I index columns based on actual query patterns, not defensively on everything."

A B-tree index: to find value 45, PostgreSQL walks 50 → 75? No → back to 25's branch → 40's leaf — only a handful of comparisons instead of scanning every row.
Index TypeBest For
B-tree (default)Equality & range queries (=, <, >, BETWEEN, ORDER BY)
GINJSONB, arrays, full-text search — indexing "contains" style lookups
HashPure equality lookups only, rarely needed over B-tree
GiSTGeometric data, nearest-neighbor search (used by PostGIS)
CREATE INDEX idx_orders_customer ON orders(customer_id);
CREATE INDEX idx_products_meta ON products USING GIN(metadata);
⚠️
Common Mistake

Adding an index on every column "just in case." Each extra index slows down every INSERT/UPDATE and consumes storage — index based on actual WHERE/JOIN/ORDER BY patterns.

⚡
Performance Note

An index on a low-cardinality column (like a boolean `is_active`) is often useless — the planner may still choose a sequential scan since half the table matches anyway.

Maintenance

05Vacuum

The cleanup crew that follows MVCC around — this directly answers "why does my table keep growing even though I delete rows?"

Simple

When you UPDATE or DELETE a row, PostgreSQL doesn't erase it immediately — it just marks it as "dead." VACUUM is the process that comes back and actually reclaims that space.

Technical

VACUUM scans tables for dead tuples left behind by MVCC, marks the space as reusable for future inserts, and updates visibility metadata so the planner and index don't waste time considering dead rows. It does NOT return space to the OS by default (that needs VACUUM FULL).

Interview-Ready

"Vacuum reclaims space from dead tuples created by MVCC's update/delete behavior, and also prevents transaction ID wraparound, which is a hard failure mode if ignored for too long."

VACUUM

Reclaims space, non-blocking

Marks dead tuple space reusable in place. Table stays online and usable throughout.

VACUUM FULL

Returns space to OS, blocking

Rewrites the entire table into a new file to physically shrink it — locks the table, so it's rarely run on a live production system without a maintenance window.

VACUUM orders;         -- routine cleanup, safe to run live
VACUUM (ANALYZE) orders; -- also refreshes planner statistics
VACUUM FULL orders;    -- rewrites table, takes a lock — use with care
⚠️
Common Mistake

Running VACUUM FULL routinely "to be safe." It locks the table and is meant for occasional, deliberate space reclamation — not a regular maintenance habit.

Automation

06Autovacuum

Manual VACUUM doesn't scale to real production traffic — autovacuum is what actually runs in the real world.

Simple

Autovacuum is a background helper that automatically runs VACUUM (and ANALYZE) for you, based on how much a table has changed — so nobody has to remember to clean up manually.

Technical

A background daemon wakes periodically, checks each table's dead-tuple ratio against configurable thresholds (`autovacuum_vacuum_scale_factor`), and triggers VACUUM/ANALYZE automatically when a table crosses that threshold.

Interview-Ready

"Autovacuum is enabled by default and is the reason most teams never manually run VACUUM — but on very large, high-churn tables, default thresholds can be too conservative and need tuning per table."

⚡
Performance Note

For very large, frequently-updated tables, teams often lower `autovacuum_vacuum_scale_factor` for that specific table so cleanup runs more often in smaller, cheaper increments instead of one huge pass.

⚠️
Common Mistake

Disabling autovacuum entirely to "reduce load." This eventually causes severe table bloat and, in extreme cases, transaction ID wraparound — a much worse production incident than the vacuum overhead itself.

🧠
Memory Trick

"Autovacuum = Vacuum on autopilot." Same job as VACUUM, just triggered automatically by dead-tuple thresholds instead of a human remembering.

Comparison

07PostgreSQL vs MySQL — Internals View

Same six concepts, viewed through how MySQL (InnoDB) does it differently — a strong way to demonstrate depth in an interview.

ConceptPostgreSQLMySQL (InnoDB)
Old row versionsKept in the same table (heap), needs VACUUMKept in a separate undo log, purged automatically
Crash recovery logWALRedo log + undo log (similar concept, different name)
Table growth from updatesTable itself can bloat until vacuumedLess prone to bloat due to undo log design
Default index typeB-tree (heap-organized table)B-tree, but clustered on the primary key
💡
Interview Tip

Say: "PostgreSQL's MVCC keeps old versions in the table itself, which is why vacuum exists as a concept — MySQL's InnoDB uses an undo log instead, so it doesn't need an equivalent vacuum step." This single sentence signals real depth.

09Scenario-Based Questions

A table used to return results instantly, but after months in production, the same query is now slow. No schema changes were made. What do you check first?
+
Model Answer
Check table/index bloat and whether autovacuum is keeping up — run EXPLAIN ANALYZE to see if the planner is still choosing an index scan, and check pg_stat_user_tables for dead tuple count. Heavy UPDATE/DELETE traffic without adequate vacuuming is the classic cause.
You add an index expecting a query to speed up, but EXPLAIN ANALYZE still shows a sequential scan. Why might that happen?
+
Model Answer
The planner may correctly judge a seq scan cheaper — e.g., the table is small, the query returns a large fraction of rows, or statistics are stale (run ANALYZE). It's not automatically a bug if the cost estimate genuinely favors a scan.
Two transactions update the same row at the same time. Walk through what happens under MVCC.
+
Model Answer
The first transaction to commit creates a new row version normally. The second transaction hits a write-write conflict — it must wait for the first to finish, then re-checks whether its own WHERE condition still applies before proceeding (or fails with a serialization error at higher isolation levels).

12Performance & Security Notes

Performance

Index write cost is real

Every index adds overhead to INSERT/UPDATE/DELETE — a table optimized purely for read speed can quietly become a write bottleneck under load.

Security

WAL files can contain sensitive data

Since WAL logs actual row changes, WAL archives used for backups/replication should be stored and transmitted with the same access controls as the primary database.

20Key Takeaways

In One Paragraph

PostgreSQL guarantees durability through WAL (log first, apply later), handles concurrency through MVCC (multiple row versions instead of read locks), picks execution strategies through a cost-based query planner, speeds up lookups with B-tree/GIN indexes, and stays healthy over time through Vacuum and Autovacuum cleaning up the dead tuples MVCC leaves behind.
