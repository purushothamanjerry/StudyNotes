01

Why Constraints Exist

A table is just rows and columns — constraints are the rules that stop it from filling up with garbage.

Problem it solves

  • Without rules, nothing stops two "unique" employee IDs, an order pointing at a customer that doesn't exist, or a salary of -5000.
  • Constraints push data validation down into the database itself, so it's enforced no matter which application, script, or person touches the table.
  • Keys additionally give MySQL a reliable way to identify a row and to relate rows across tables.

Real-world example

Think of a college admission form: a PRIMARY KEY is your unique roll number; a FOREIGN KEY links your enrolled course to a real course in the catalog; UNIQUE stops two students from registering the same email; NOT NULL means the name field can't be left blank; CHECK rejects an age below 15; DEFAULT auto-fills "Pending" as your application status if you don't set one.

Interview Tip

Interviewers separate two layers here: constraints (PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK, DEFAULT, NOT NULL) are things you literally write in DDL. Key theory (candidate, super, alternate, composite, surrogate) is relational-model vocabulary that explains why you chose the constraints you did. Freshers often blur the two — keep them distinct in your answers.

02

PRIMARY KEY

The column (or set of columns) that uniquely identifies every row in a table — chosen from among the candidate keys.

primary_key.sql 
CREATE TABLE employee (
  id INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(100) NOT NULL
);

How MySQL internally works

In InnoDB, the PRIMARY KEY isn't just a constraint — it is the physical storage order of the table (a clustered index). Every row is stored sorted by its primary key, and every secondary index secretly stores the primary key value to look the full row up. This is why a table without an explicit primary key still gets an internal hidden one generated by InnoDB.

Rules

Only one PRIMARY KEY per table; it is implicitly NOT NULL + UNIQUE; can span multiple columns (composite primary key).

Common Mistake

Assuming a table "doesn't need" a primary key. Every InnoDB table benefits from one — without it, InnoDB adds an invisible 6-byte row ID and clustering becomes harder to reason about or replicate reliably.

03

FOREIGN KEY

A column that references the PRIMARY KEY (or a UNIQUE key) of another table, enforcing that the relationship always points to something real.

foreign_key.sql 
CREATE TABLE employee (
  id INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(100),
  department_id INT,
  FOREIGN KEY (department_id) REFERENCES department(id)
    ON DELETE SET NULL
    ON UPDATE CASCADE
);
✗ ERROR 1452: Cannot add or update a child row: a foreign key constraint fails (department_id = 99 does not exist in department)

ON DELETE / ON UPDATE Actions

Action Behaviour on parent DELETE/UPDATE
CASCADE Automatically deletes/updates matching child rows too
SET NULL Sets the child's foreign key column to NULL
RESTRICT / NO ACTION Blocks the parent operation if matching child rows exist (MySQL default)
Warning

Foreign keys are only enforced by InnoDB, MySQL's default storage engine — the older MyISAM engine silently ignores them. Always confirm the engine in an interview answer about referential integrity.

04

UNIQUE

Guarantees no two rows share the same value in a column (or column combination) — but unlike PRIMARY KEY, it allows NULLs.

unique_constraint.sql 
CREATE TABLE employee (
  id INT PRIMARY KEY,
  email VARCHAR(150) UNIQUE,
  ssn VARCHAR(20) UNIQUE
);
Interview Tip

Classic trap question: "Can a UNIQUE column have multiple NULLs?" In MySQL, yes — NULL is never considered equal to another NULL, so multiple NULLs don't violate uniqueness (this differs from some other databases like SQL Server, which historically allowed only one NULL).

05

CHECK

Enforces a boolean condition on every row — fully supported from MySQL 8.0.16 onward (earlier versions parsed but silently ignored it).

check_constraint.sql 
CREATE TABLE employee (
  id INT PRIMARY KEY,
  salary DECIMAL(10,2) CHECK (salary > 0),
  age INT CHECK (age >= 18)
);
Common Mistake

Assuming CHECK constraints always worked in MySQL. Before 8.0.16, MySQL accepted the syntax but never enforced it — a well-known interview "gotcha" specific to MySQL's version history.

06

DEFAULT

Supplies an automatic value for a column when an INSERT doesn't specify one.

default_constraint.sql 
CREATE TABLE employee (
  id INT PRIMARY KEY,
  status VARCHAR(20) DEFAULT 'ACTIVE',
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO employee (id) VALUES (1);
-- status becomes 'ACTIVE', created_at becomes now() automatically
Best Practice

Prefer database-level DEFAULT for audit columns like created_at over setting them in application code — it guarantees consistency even for rows inserted by scripts, migrations, or another service entirely.

07

NOT NULL

The simplest constraint — a column must always contain a value; MySQL rejects any INSERT or UPDATE that would leave it empty.

not_null.sql 
CREATE TABLE employee (
  id INT PRIMARY KEY,
  name VARCHAR(100) NOT NULL
);
Interview Tip

NOT NULL is a column-level constraint only — it can't span multiple columns like CHECK or UNIQUE can. If you need "at least one of column A or B must be filled," you need a CHECK constraint instead.

09

Candidate Key

Any column (or minimal column combination) that could, on its own, uniquely identify every row.

In our employee table: id, ssn, and email are all candidate keys — each independently guarantees uniqueness. MySQL doesn't have a literal CANDIDATE KEY keyword; you express candidacy by making each one either the PRIMARY KEY or a UNIQUE constraint.

Key Rule

A candidate key must be minimal — no column inside it can be removed without losing uniqueness. That minimality is exactly what separates a candidate key from a super key.

10

Super Key

Any set of columns that uniquely identifies a row — including extra, unnecessary columns.

Every candidate key is a super key, but not every super key is a candidate key. {id} is a super key. So is {id, first_name} — it's still unique because id alone already guarantees that — but it's not minimal, so it's not a candidate key.

Common Mistake

Saying "super key" when you mean "candidate key," or vice versa. The one-line test: is every column in the set actually necessary? If yes → candidate key. If some are redundant → just a super key.

11

Alternate Key

Any candidate key that was not chosen as the primary key.

If id becomes the PRIMARY KEY, then ssn and email — still perfectly valid unique identifiers — become alternate keys. In MySQL you enforce them with a UNIQUE constraint, since the PRIMARY KEY slot is already taken.

alternate_key.sql 
CREATE TABLE employee (
  id INT PRIMARY KEY,           -- chosen candidate key
  ssn VARCHAR(20) UNIQUE,     -- alternate key
  email VARCHAR(150) UNIQUE   -- alternate key
);
12

Composite Key

A key made of two or more columns together, where no single column alone is unique.

Classic example: an order_items table where neither order_id nor product_id is unique alone, but the pair together is.

composite_key.sql 
CREATE TABLE order_items (
  order_id INT,
  product_id INT,
  quantity INT NOT NULL,
  PRIMARY KEY (order_id, product_id)
);
Interview Tip

A composite key is a description of how many columns a key uses — it can describe a primary key, a candidate key, or a unique key. It's an orthogonal concept, not a rival to those terms.

13

Surrogate Key

An artificial, system-generated identifier with no real-world business meaning — chosen purely to identify a row.

id INT AUTO_INCREMENT is a surrogate key: it means nothing outside the database. Compare that to a natural key like ssn or email, which has meaning in the real world independent of the database.

Best Practice

Product companies almost always default to surrogate keys as the primary key, even when a natural key exists — natural keys can change (an email gets updated) or turn out to not be as unique as assumed (two people sharing a legacy ID format).

14

Common Mistakes & Performance Notes

Forgetting FOREIGN KEY needs InnoDB ▾
MyISAM tables accept the FOREIGN KEY syntax but never actually enforce it — always confirm engine = InnoDB when referential integrity matters.
Confusing UNIQUE with PRIMARY KEY ▾
UNIQUE allows multiple NULLs and a table can have many UNIQUE constraints, but only one PRIMARY KEY, which is always NOT NULL.
Adding too many indexes/keys "just in case" ▾
Every UNIQUE/FOREIGN KEY constraint typically creates a backing index, which speeds up reads but slows down every INSERT/UPDATE/DELETE. Add only what the access patterns actually need.
Using a natural key as PRIMARY KEY that later changes ▾
If email is the primary key and a user changes their email, every foreign key referencing it must cascade-update — expensive and risky at scale. Prefer a surrogate key instead.

Spring Boot Relation

JPA/Hibernate annotations map almost one-to-one onto these constraints.

SQL Concept JPA / Hibernate Annotation
PRIMARY KEY @Id, with @GeneratedValue for surrogate keys
FOREIGN KEY @ManyToOne / @JoinColumn
UNIQUE @Column(unique = true) or @Table(uniqueConstraints = ...)
NOT NULL @Column(nullable = false), often paired with @NotNull (Bean Validation)
CHECK No direct annotation — usually a native @Check (Hibernate-specific) or enforced in the DB migration script
Composite Key @EmbeddedId or @IdClass
16

Natural Key vs Surrogate Key

  • Has real-world meaning (email, SSN, ISBN) — self-documenting in queries.
  • Risk: can change over time, forcing cascading updates.
  • Risk: "uniqueness" assumptions can break (duplicate SSNs across systems, format changes).
  • Never changes, has no business meaning, always safe to reference.
  • Smaller and faster to index (a 4-byte INT vs a long VARCHAR).
  • Downside: an extra join or lookup is sometimes needed to get to human-meaningful data.
17

Memory Tricks

Key Family

"Super holds Candidates, Candidate becomes Primary or stays Alternate" — super ⊇ candidate ⊇ {primary + alternates}.

Constraints Sentence

"Please Find Unique Checks Done Nicely" → Primary, Foreign, Unique, Check, Default, NOT NULL.

Surrogate vs Natural

"Surrogate is Synthetic" — both start with S, both are artificial/meaningless outside the DB.

Summary

Constraints (PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK, DEFAULT, NOT NULL) are rules you write in DDL to keep data valid and relationships intact. Key theory (candidate, super, alternate, composite, surrogate) is the relational-model vocabulary explaining which columns qualify as identifiers and why one was chosen over the others. Every candidate key is a super key; every unchosen candidate key becomes an alternate key; a key spanning multiple columns is composite regardless of which category it falls into; and product teams almost always prefer an artificial surrogate key over a natural one for stability at scale.
