Isolation Levels — How Much Can Transactions See of Each Other?

Two transactions run at the same time on the same rows. Isolation level is the rulebook for exactly how much of one transaction's in-progress work the other is allowed to see — the dial between "fast but leaky" and "slow but airtight."

Two people, one bank row:
-- Txn A
UPDATE accounts SET balance = 500 WHERE id=1;
-- not committed yet...

-- Txn B, at the same instant
SELECT balance FROM accounts WHERE id=1;
Does Txn B see 500 (uncommitted) or the old value? The answer depends entirely on the isolation level — and MySQL's default, REPEATABLE READ, is stricter than most databases' default.
01

Why Isolation Levels Exist

Running transactions fully isolated (one at a time) is perfectly safe but painfully slow. Running them fully concurrent is fast but lets transactions corrupt each other's view of the data. Isolation levels are the trade-off dial the SQL standard defines between the two.

Problem it solves

Concurrency vs correctness

Multiple users hit the same rows simultaneously; the database must decide what each one is allowed to see mid-flight.

Predictability

Without a defined isolation level, "what will my SELECT return?" has no reliable answer during concurrent writes.

Anomaly prevention

Each level exists specifically to rule out one or more of: dirty reads, non-repeatable reads, phantom reads.

Real-world example

Two bank tellers process withdrawals from the same joint account at the same second. If Teller B reads Teller A's uncommitted withdrawal (a dirty read) and acts on it, then Teller A's transaction rolls back — the account is now wrong. Isolation levels are exactly the rule that prevents or permits this.

Interview one-liner

"Isolation level controls which of the three classic anomalies — dirty read, non-repeatable read, phantom read — a transaction is protected from, at the cost of more locking and less concurrency as you go stricter."

02

The Three Classic Anomalies

Dirty Read

Reading another transaction's uncommitted changes — data that might be rolled back a moment later, meaning you acted on something that never really happened.

Txn A
UPDATE balance = 500 -- uncommitted
Txn B
SELECT balance -- reads 500, the dirty value
Txn A
ROLLBACK -- 500 never actually happened

Non-Repeatable Read

Reading the same row twice in one transaction and getting different values, because another transaction committed an update to it in between.

Txn B
SELECT balance -- reads 1000
Txn A
UPDATE balance=800; COMMIT;
Txn B
SELECT balance -- same query, now reads 800

Phantom Read

Re-running the same range query in one transaction and getting new or missing rows, because another transaction inserted/deleted rows matching that range and committed in between.

Txn B
SELECT * WHERE salary>90000 -- 5 rows
Txn A
INSERT new row salary=95000; COMMIT;
Txn B
SELECT * WHERE salary>90000 -- now 6 rows, a "phantom"
Interview distinction

Non-repeatable read = an existing row changed value. Phantom read = the set of rows itself changed (new/removed rows) for the same WHERE condition. Interviewers frequently test whether you can tell these apart.

How MySQL Enforces It — MVCC & Next-Key Locks

InnoDB implements isolation mostly through MVCC (Multi-Version Concurrency Control): instead of blocking readers, every row keeps hidden versioning info, and each transaction reads the version of the row that existed at the right point in time for its isolation level.

  1. Every row has hidden DB_TRX_ID (which transaction last changed it) and a pointer to its previous version in the undo log.
  2. At REPEATABLE READ, a transaction takes a consistent snapshot at the time of its first read, and every subsequent plain SELECT in that transaction sees that same snapshot — this is why non-repeatable reads don't occur.
  3. To also prevent phantom reads, InnoDB adds next-key locks (a row lock plus a gap lock on the range before it) for locking reads (SELECT ... FOR UPDATE) and DML — blocking other transactions from inserting into the gap.
  4. This is why MySQL's REPEATABLE READ, unusually among databases, already prevents most phantom reads in practice — even though the SQL standard only requires that at SERIALIZABLE.
Interview trap

"Does MySQL's REPEATABLE READ fully match the SQL standard's definition?" — It goes further: thanks to next-key locking, InnoDB's REPEATABLE READ prevents phantom reads in most locking-read scenarios, which the standard doesn't require until SERIALIZABLE.

05

Read Uncommitted

The weakest level. Transactions can see each other's uncommitted changes. No consistent snapshot, no locking on plain reads.

SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

Allows: dirty reads, non-repeatable reads, phantom reads. Almost never used in production — mainly relevant for approximate analytics where absolute correctness doesn't matter and speed does.

06

Read Committed

A transaction only ever sees data that has been committed by other transactions — but takes a fresh snapshot on every single statement, not once per transaction.

SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

Prevents: dirty reads. Still allows: non-repeatable reads and phantom reads, because each new statement re-reads the latest committed state — which can differ from the last statement's read.

Interview note

Read Committed is the default in PostgreSQL and Oracle — a common trick question is assuming it's also MySQL's default. It isn't; MySQL defaults to REPEATABLE READ.

07

Repeatable Read — MySQL's Default

A transaction takes one consistent snapshot at its first read and reuses it for every plain SELECT for the rest of the transaction — so the same query always returns the same rows and values.

SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ; -- MySQL default

Prevents: dirty reads, non-repeatable reads, and (thanks to InnoDB's next-key locking on locking reads/DML) most phantom reads in practice. Standard-wise: the SQL spec only guarantees the first two at this level — MySQL's implementation is stricter than the bare minimum.

Best practice

Leave REPEATABLE READ as the default for typical OLTP workloads — it gives strong consistency guarantees without the full locking cost of SERIALIZABLE.

08

Serializable

The strictest level. Transactions behave as if they ran one at a time, in some serial order — InnoDB implements this by converting every plain SELECT into a locking read (as if it were SELECT ... LOCK IN SHARE MODE).

SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;

Prevents: dirty reads, non-repeatable reads, phantom reads — all three. Cost: heavy locking, much lower concurrency, higher chance of lock waits and deadlocks under load.

Interview trap

"Isn't SERIALIZABLE always the safest choice?" — Technically yes for correctness, but it can cripple throughput on a busy OLTP system. Most teams reach for REPEATABLE READ plus explicit locking (FOR UPDATE) on the specific statements that truly need it, rather than SERIALIZABLE everywhere.

09

Spring Boot Relation

Spring lets you set the isolation level per-transaction with @Transactional, overriding the connection/database default for just that method.

@Transactional(isolation = Isolation.REPEATABLE_READ)
public void transferFunds(Long fromId, Long toId, BigDecimal amount) {
    Account from = accountRepo.findById(fromId).orElseThrow();
    Account to = accountRepo.findById(toId).orElseThrow();
    from.debit(amount);
    to.credit(amount);
}
Interview angle

"When would you raise the isolation level in Spring, versus just using pessimistic locking?" — Raise isolation for correctness guarantees across the whole transaction; use @Lock(LockModeType.PESSIMISTIC_WRITE) or explicit SELECT ... FOR UPDATE when only a specific row needs protecting, to avoid paying the cost everywhere.

11

Advantages · Disadvantages · When to Use / Avoid

Advantages of stricter levels

Predictable, correct results even under heavy concurrency · eliminates entire classes of subtle bugs · simplifies application-level reasoning about data.

Disadvantages of stricter levels

More locking, more blocked transactions, higher chance of deadlocks, lower throughput under load.

When to use higher isolation

Financial transfers, inventory counts, anything where a stale or dirty read causes real-world incorrect decisions.

When lower isolation is fine

Dashboards, analytics, approximate counts, read-heavy reporting where a slightly stale view is an acceptable trade for speed.

12

Performance Notes, Beginner Mistakes & Best Practices

Performance note

Higher isolation levels increase lock contention and the risk of deadlocks under concurrent write-heavy workloads — measure before assuming SERIALIZABLE is "just safer."

Beginner mistake

Assuming MySQL's default isolation level is Read Committed (true for Postgres/Oracle, not MySQL). MySQL/InnoDB defaults to REPEATABLE READ.

Beginner mistake

Confusing non-repeatable read (a row's value changed) with phantom read (the row set changed). They're tested separately in interviews.

Best practice

Default to REPEATABLE READ, and reach for explicit SELECT ... FOR UPDATE locking or a raised isolation level only for the specific transactions that truly need stronger guarantees.

Interview, Scenario & Company Questions

What is MySQL's default isolation level?+
REPEATABLE READ, for the InnoDB storage engine.
How does InnoDB mostly avoid phantom reads at REPEATABLE READ, even though the standard doesn't require it?+
Via next-key locks — a row lock combined with a gap lock — which block other transactions from inserting new rows into the locked range.
What is MVCC?+
Multi-Version Concurrency Control — InnoDB keeps multiple historical versions of a row (via the undo log) so readers can see a consistent snapshot without blocking writers.
A report re-runs the same SELECT twice in one transaction and gets different row counts. What's happening, and how do you fix it?+
A phantom read at too low an isolation level (Read Committed) or without a snapshot. Move to REPEATABLE READ, or wrap the query in a single consistent-read transaction.
Two transactions both read a stock quantity, both decide it's sufficient, both deduct — resulting in a negative stock. What went wrong?+
A classic lost-update problem. Plain SELECTs don't lock the row. Fix with SELECT ... FOR UPDATE (pessimistic locking) or an optimistic-locking version column, not just a higher isolation level alone.

ZohoTCS DigitalInfosysAccentureCapgeminiCognizantHCLWipro

[Zoho / Product companies] Why might you deliberately choose Read Committed over Repeatable Read?+
For workloads that need to see the latest committed data on every statement (e.g. live dashboards) and can tolerate non-repeatable reads in exchange for less locking overhead.
[TCS Digital / Infosys] Explain the difference between a dirty read and a non-repeatable read with an example.+
Dirty read: seeing another transaction's uncommitted change. Non-repeatable read: re-reading a row and seeing a different value because another transaction committed a change in between — the first involves uncommitted data, the second committed data.
[Accenture / Capgemini / Cognizant] Is Serializable always the right choice for a banking application?+
Not automatically — REPEATABLE READ combined with targeted row locking (SELECT ... FOR UPDATE) on the specific balance-changing statements often gives the needed correctness with far less contention than SERIALIZABLE everywhere.

Memory Tricks

"DNP" ladder

Each step up removes one letter of trouble: Read Uncommitted (D+N+P possible) → Read Committed (N+P) → Repeatable Read (P mostly gone) → Serializable (none).

Dirty = "not even real yet"

You're reading something that might be rolled back — it was never really true.

Phantom = "new ghost rows"

Not a value changing — a whole new row appearing (or disappearing) in your range query.

Summary

Isolation levels govern how much of one transaction's work another can see while both run concurrently. Four SQL-standard levels — Read Uncommitted, Read Committed, Repeatable Read, Serializable — trade correctness for concurrency in that order. MySQL/InnoDB defaults to Repeatable Read and uses MVCC plus next-key locks to prevent dirty reads, non-repeatable reads, and (mostly) phantom reads without full serial execution.

Revision Notes

  • Dirty read = reading uncommitted data
  • Non-repeatable read = same row, different value on re-read
  • Phantom read = same range query, different row set on re-read
  • MySQL default = REPEATABLE READ (not Read Committed — that's Postgres/Oracle's default)
  • MVCC gives readers a consistent snapshot without blocking writers
  • Next-key locks (row + gap) are why MySQL's Repeatable Read mostly avoids phantoms too
  • Serializable = strictest, most locking, lowest concurrency
