01

Why Subqueries Exist

Some questions can't be answered in a single pass over a table — you first need to compute something, then filter using it.

Problem it solves

  • "Employees earning more than the company average" needs the average computed before you can filter — a subquery nests that computation inside the outer query.
  • "Departments that have at least one employee" needs to check for the existence of related rows without fetching them.
  • Subqueries let you express these multi-step questions in a single SQL statement instead of round-tripping to the application twice.

Real-world example

An HR dashboard showing "employees who earn more than their own department's average salary" needs a subquery that recalculates the average per department for every row — a correlated subquery, and one of the most commonly asked SQL problems in interviews.

Interview Tip

Interviewers classify subqueries along two independent axes: how many rows/columns it returns (single-row vs multi-row vs multi-column) and whether it depends on the outer query (correlated vs non-correlated). Keep these two classifications separate in your answers — they're not the same distinction.

02

Single Row Subquery

Returns exactly one row and one column — the only kind of subquery you can compare directly with =, >, <, etc.

single_row_subquery.sql
SELECT name, salary
FROM employee
WHERE salary > (
  SELECT AVG(salary) FROM employee
);
✓ Inner query resolves first → avg(salary) = 52000

Common Mistake

Using = with a subquery that can return more than one row throws ERROR 1242: Subquery returns more than 1 row. Always be sure the inner query is truly single-row before comparing with a plain operator.

03

Multiple Row Subquery

Returns many rows (still one column) — must be used with IN, ANY, ALL, or EXISTS, never a plain comparison operator.

multi_row_subquery.sql
SELECT name
FROM employee
WHERE department_id IN (
  SELECT id FROM department WHERE location = 'Chennai'
);
Warning

If the multi-row subquery's result can contain NULL and you use NOT IN, the entire outer query can silently return zero rows — the same NULL trap covered for the IN operator elsewhere in this series.

04

Correlated Subquery

A subquery that references a column from the outer query — so it can't be evaluated on its own, and MySQL conceptually re-runs it once per outer row.

correlated_subquery.sql
SELECT e1.name, e1.salary, e1.department_id
FROM employee e1
WHERE e1.salary > (
  SELECT AVG(e2.salary)
  FROM employee e2
  WHERE e2.department_id = e1.department_id  -- references the outer row
);

This finds employees earning more than their own department's average — impossible with a plain single-row subquery, because the "average" is different for every outer row.

Best Practice

Modern MySQL's optimizer can sometimes rewrite correlated subqueries into semi-joins internally for better performance — but you should still reason about (and be ready to explain) the logical per-row execution model in interviews, since that's what's actually being tested.

Interview Tip

A non-correlated subquery runs once and its result is reused; a correlated subquery is logically re-evaluated for every candidate row of the outer query — which is exactly why correlated subqueries are more expensive on large tables and why EXISTS is often preferred over IN for them.

06

IN (with Subqueries)

Checks membership against the full set of values a subquery returns.

in_subquery.sql
SELECT name FROM employee
WHERE department_id IN (SELECT id FROM department WHERE active = 1);

Typically non-correlated — the subquery's value list is computed once and the outer query checks each row against it.

07

ANY

A comparison operator combined with a subquery — TRUE if the comparison holds for at least one value returned.

any_subquery.sql
SELECT name, salary FROM employee
WHERE salary > ANY (
  SELECT salary FROM employee WHERE department_id = 3
);
-- equivalent in spirit to: salary > MIN(that department's salaries)
Interview Tip

> ANY (subquery) means "greater than at least one value," which is logically the same as being greater than the minimum of that set. SOME is a standard-SQL synonym for ANY in MySQL.

08

ALL

TRUE only if the comparison holds for every value returned by the subquery.

all_subquery.sql
SELECT name, salary FROM employee
WHERE salary > ALL (
  SELECT salary FROM employee WHERE department_id = 3
);
-- equivalent in spirit to: salary > MAX(that department's salaries)

ANY vs ALL, Side by Side

ExpressionPlain EnglishEquivalent Aggregate
> ANY (...)Greater than at least one value> MIN(...)
> ALL (...)Greater than every value> MAX(...)
< ANY (...)Less than at least one value< MAX(...)
< ALL (...)Less than every value< MIN(...)
Common Mistake

Mixing up ANY and ALL — remembering "ANY = easier to satisfy (MIN-like), ALL = harder to satisfy (MAX-like)" for a > comparison avoids the confusion under interview pressure.

09

EXISTS

TRUE if the (usually correlated) subquery returns at least one row — MySQL stops scanning the instant it finds a match.

exists_subquery.sql
SELECT d.name FROM department d
WHERE EXISTS (
  SELECT 1 FROM employee e WHERE e.department_id = d.id
);
Best Practice

Use SELECT 1 (not SELECT *) inside an EXISTS subquery — the actual column selected is irrelevant, since EXISTS only cares whether a row was found, and 1 makes that explicit to any reader.

10

Common Mistakes & Performance Notes

Using = with a subquery that can return multiple rows ▾
Throws "Subquery returns more than 1 row." Use IN, ANY, ALL, or EXISTS for multi-row subqueries instead.
NOT IN with a NULL-containing subquery ▾
Silently returns zero rows for the entire outer query — the single most common subquery bug. Prefer NOT EXISTS when NULLs are possible.
Writing a correlated subquery when a JOIN would do ▾
If you just need matching columns from both tables, a JOIN is usually both clearer and faster than a correlated subquery re-evaluated per row.
Forgetting the outer alias inside a correlated subquery ▾
If both tables in a correlated subquery use the same name without distinct aliases, MySQL can't tell which column belongs to the outer vs inner query — always alias both sides explicitly.

12

Subquery vs JOIN

  • You only need to filter/check, not fetch columns from the related table.
  • The logic is naturally a "for this row, is X true" question — EXISTS reads very clearly.
  • You need a single aggregate value (AVG, MAX) to compare against, computed once.
  • You need actual columns from both tables in the output.
  • You're aggregating across the relationship (COUNT/SUM per group).
  • Performance testing (via EXPLAIN) shows the JOIN plan is cheaper — MySQL's optimizer sometimes rewrites subqueries into joins anyway, but not always.
13

Memory Tricks

ANY vs ALL

"ANY is easy (MIN), ALL is tough (MAX)" — for a > comparison, ANY only needs to beat the smallest value.

Correlated = Loop

"Correlated subqueries Circle back" — they reference the outer row and conceptually re-run per row, like a loop.

EXISTS over IN

"EXISTS Ends early" — it short-circuits on first match and is safe with NULLs, unlike NOT IN.

Find employees who earn more than their own department's average salary ▾
SELECT e1.name, e1.salary
FROM employee e1
WHERE e1.salary > (
  SELECT AVG(e2.salary) FROM employee e2
  WHERE e2.department_id = e1.department_id

Find the second highest salary using a subquery ▾
SELECT MAX(salary) FROM employee
WHERE salary < (SELECT MAX(salary) FROM employee);
Find departments with no employees using NOT EXISTS ▾
SELECT d.name FROM department d
WHERE NOT EXISTS (
  SELECT 1 FROM employee e WHERE e.department_id = d.id
);

Summary

Subqueries let one query answer a question that needs a computed or existence-based sub-question first. Classify them by row count (single vs multiple) and by dependency (correlated vs non-correlated) — these are separate, complementary distinctions. IN and ANY/ALL express set-membership and set-comparison; EXISTS expresses existence and is usually the safest, fastest choice for correlated existence checks. Understanding that a correlated subquery is logically re-evaluated per outer row — while a non-correlated one runs once — is the single fact interviewers use most to separate candidates who memorised syntax from candidates who understand execution.
