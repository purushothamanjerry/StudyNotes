Module 17 — MySQL Interview Track ⭐ Capstone Module

Performance Tuning

A query that returns correct results but takes 8 seconds isn't done — it's broken. This module is where every earlier concept (indexes, joins, aggregation, pagination) gets stress-tested: reading EXPLAIN, hunting slow queries, and fixing the specific patterns that quietly wreck production performance.

⭐ Why this module is the capstone

Every prior module becomes a performance lever here

Schema design (Module 3), joins (Module 8), aggregation (Module 6) — all of it directly determines how fast or slow your queries run. Interviewers use performance questions specifically to test whether you understand the "why" underneath the syntax you've already learned.

Real-world analogy

EXPLAIN is like asking Google Maps for the route before driving — it shows you the plan (which "roads"/indexes MySQL will take) so you can spot a bad detour before you're stuck in traffic for 8 seconds per request.

Problem it solves

A functionally correct query can still take down a production system under load. Performance tuning is the discipline of making sure "correct" and "fast enough" are both true, not just the first one.

01 · Diagnostic Tool

EXPLAIN

Prefixing any query with EXPLAIN shows MySQL's execution plan without running it — the single most important habit for anyone touching production SQL.

explain.sql
EXPLAIN SELECT e.first_name, d.dept_name
FROM employees e
JOIN departments d ON e.dept_id = d.id
WHERE e.salary > 50000;
tabletypekeyrowsExtra
eALLNULL18420Using where
deq_refPRIMARY1

01The columns that actually matter

ColumnWhat to look for
typeAccess method — const/eq_ref/ref is great, ALL means a full table scan (red flag)
keyWhich index was actually used — NULL means no index was used at all
rowsEstimated rows MySQL expects to examine — lower is better, a strong cost proxy
Extra"Using filesort" / "Using temporary" are common performance warnings worth investigating
Interview trap

The `e` table above shows type: ALL despite filtering on salary — because there's no index on that column. The fix (add an index) is the direct segue into Index Optimization below.

Beyond EXPLAIN

EXPLAIN ANALYZE (MySQL 8.0.18+) actually executes the query and reports real timing per step, not just estimates — mention this for extra credit in interviews.

02Interview questions

What does "type: ALL" mean in EXPLAIN, and why is it bad?+

It means MySQL is doing a full table scan — reading every row to find matches, instead of using an index to jump directly to relevant rows. On large tables this is the single biggest performance red flag.

What's the difference between EXPLAIN and EXPLAIN ANALYZE?+

EXPLAIN shows the optimizer's estimated plan without running the query. EXPLAIN ANALYZE actually executes it and reports real measured timing and row counts per step, giving ground truth instead of an estimate.

02 · Diagnostics

Slow Queries

Before you can fix a slow query, you have to find it — MySQL's slow query log is the production-grade way to do that.

slow_query_log.sql
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1; -- log any query taking > 1 second
SHOW VARIABLES LIKE 'slow_query_log_file';
→ Every query exceeding 1 second is now appended to the slow query log with full timing and row-examination stats
→ Tools like mysqldumpslow or pt-query-digest summarize the log by frequency × cost

01Common causes, ranked by frequency

Missing index

By far the most common cause — a WHERE/JOIN/ORDER BY column with no supporting index forces a full scan.

Function on an indexed column

WHERE YEAR(created_at)=2026 disables index usage on created_at entirely.

Implicit type conversion

Comparing an indexed INT column to a string literal can silently prevent index use.

Large OFFSET pagination

MySQL still scans and discards every skipped row before returning the page.

N+1 query pattern

A loop issuing one query per row instead of one batched query — extremely common in careless JPA/Hibernate code.

Lock contention

Long-running transactions holding row/table locks, blocking other queries from proceeding.

The N+1 trap — asked constantly for Spring Boot roles

A JPA @OneToMany relationship fetched lazily inside a loop issues 1 query for the parent list, then 1 additional query per child — 101 queries for 100 rows. Fix with JOIN FETCH in JPQL, an @EntityGraph, or a single batched query.

02Interview questions

Asked at Infosys: How would you identify the slowest queries in a production MySQL instance? Infosys+

Enable the slow query log with an appropriate long_query_time threshold, then analyze it with mysqldumpslow or pt-query-digest to rank queries by total time × frequency (not just single-query duration) — a frequently-run "slightly slow" query often costs more overall than a rare "very slow" one.

03 · Optimization

Index Optimization

Indexes are the single highest-leverage performance tool in MySQL — and the easiest to misuse.

index_optimization.sql
-- Single-column index
CREATE INDEX idx_employees_salary ON employees(salary);

-- Composite index -- column order matters!
CREATE INDEX idx_orders_status_date ON orders(status, order_date);

-- Covering index -- query can be satisfied from the index alone
CREATE INDEX idx_covering ON employees(dept_id, first_name, salary);
SELECT first_name, salary FROM employees WHERE dept_id = 2;
→ The covering index query never touches the table's data pages at all — "Using index" appears in EXPLAIN's Extra column
→ This is significantly faster than a normal index lookup, which still needs one extra hop to fetch the row

01The leftmost-prefix rule

A composite index on (status, order_date) can serve queries filtering on status alone, or on status AND order_date together — but not a query filtering on order_date alone. The index is only usable left-to-right, like a phone book sorted by last name then first name: useless for finding everyone named "Rahul" without knowing the last name too.

Query filters onCan use idx(status, order_date)?
statusYes
status AND order_dateYes
order_date onlyNo — leftmost column skipped
Interview trap

"Should you index every column?" — No. Every index speeds up reads but slows down every INSERT/UPDATE/DELETE (each index must also be maintained) and consumes disk space. Index columns actually used in WHERE, JOIN, and ORDER BY — not every column defensively.

Best practice

Put the highest-selectivity (most distinct values) or equality-filtered column first in a composite index when the access pattern allows it — this lets MySQL narrow down the fewest matching rows earliest.

02Interview questions

Asked at Accenture: What is a covering index and why is it fast? Accenture+

An index that contains every column the query needs, so MySQL can answer the query by reading only the index (a smaller, sorted structure) without a second lookup into the actual table data (the clustered index) — visible as "Using index" in EXPLAIN.

Scenario: You add an index but EXPLAIN still shows type: ALL. Why might MySQL ignore your new index? Scenario+

Common causes: a function wraps the indexed column in WHERE, a type mismatch forces conversion, the query doesn't respect the leftmost-prefix rule for a composite index, or the optimizer estimates the table is small/low-selectivity enough that a full scan is actually cheaper than an index lookup.

04 · Optimization

Query Optimization

Rewriting the query itself, independent of indexing — the patterns that turn an 8-second query into an 80-millisecond one.

-- SLOW: function on indexed column disables the index
SELECT * FROM orders WHERE YEAR(order_date) = 2026;

-- FAST: rewritten as a sargable range, index-friendly
SELECT * FROM orders
WHERE order_date >= '2026-01-01' AND order_date < '2027-01-01';
-- EXISTS often outperforms IN with a subquery on large sets
SELECT * FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- MySQL 8's optimizer often rewrites simple IN subqueries to joins/semi-joins,
-- but EXISTS with a well-indexed correlated column is a safe, explicit choice
-- SLOW: join first, then filter a huge intermediate result
SELECT * FROM orders o JOIN order_items oi ON oi.order_id=o.id
WHERE o.status = 'PENDING';

-- FAST: MySQL's optimizer usually pushes WHERE down automatically,
-- but for complex queries, pre-filtering in a subquery/CTE helps it plan better
SELECT * FROM (SELECT * FROM orders WHERE status='PENDING') o
JOIN order_items oi ON oi.order_id=o.id;
Interview tip

The term to know: a condition is "sargable" (Search ARGument ABLE) if MySQL can use an index to evaluate it directly. Wrapping a column in a function almost always makes a condition non-sargable.

01Interview questions

What does "sargable" mean, and give an example of a non-sargable condition?+

A condition MySQL can evaluate using an index seek rather than a full scan. WHERE UPPER(email) = 'X@CORP.COM' is non-sargable because UPPER() must be computed per row before comparison, disabling the index on email.

05 · Pattern

Pagination

Every list endpoint in a REST API paginates — and the naive approach degrades badly at scale.

OFFSET page 1
4 ms
OFFSET page 1,000
340 ms
OFFSET page 10,000
2,900 ms
Keyset page (any depth)
3 ms
pagination.sql
-- OFFSET pagination: gets slower as page number grows
SELECT * FROM products ORDER BY id LIMIT 20 OFFSET 200000;

-- Keyset (seek) pagination: constant time at any depth
SELECT * FROM products
WHERE id > 200000 -- last_seen_id from the previous page
ORDER BY id LIMIT 20;
→ Keyset pagination uses the index to seek directly to the right spot; OFFSET must still count through every skipped row first
Interview trap

"Why is LIMIT 20 OFFSET 200000 slow?" — MySQL cannot skip directly to row 200,000; it must scan and discard the first 200,000 matching rows (even using an index) before returning the page you asked for.

Spring Boot relation

Spring Data JPA's Pageable defaults to OFFSET-based paging. For deep or high-traffic pagination, use a Slice query with a keyset WHERE clause instead of relying on PageRequest.of(pageNumber, size) alone.

01Interview questions

Scenario: Your product listing API gets noticeably slower as users click deeper into pagination. How do you fix it? Scenario+

Switch from OFFSET-based to keyset (seek) pagination: track the last row's sort key (e.g. id) from the current page, and query WHERE id > last_seen_id ORDER BY id LIMIT n for the next page — constant-time at any depth, provided that column is indexed.

06 · Pattern

Batch Insert

Bulk-loading data one row per round trip is one of the most common fresher performance mistakes — and one of the easiest to fix.

batch_insert.sql
-- SLOW: 10,000 separate round trips
-- for (row in rows) { INSERT INTO products (name, price) VALUES (?, ?); }

-- FAST: one round trip, one statement, thousands of rows
INSERT INTO products (name, price) VALUES
  ('Widget A', 199.00),
  ('Widget B', 249.00),
  -- ... thousands more rows ...
  ('Widget Z', 399.00);
→ Single-row loop: ~10,000 round trips, each with network + transaction overhead — often 30-60 seconds
→ Batched insert (500-1000 rows/statement): the same 10,000 rows in roughly 1-2 seconds

01Practical batching rules

Chunk large batches

Don't put all 100,000 rows in one statement — respect max_allowed_packet; batches of 500-1000 rows per statement are a common sweet spot.

Wrap in a transaction

Wrapping multiple batch statements in one transaction avoids per-statement commit overhead (autocommit off, then one COMMIT at the end).

Disable/defer indexes for huge loads

For very large one-time bulk loads, some teams drop secondary indexes, load data, then rebuild indexes — much faster than maintaining them per row.

Hibernate batching

spring.jpa.properties.hibernate.jdbc.batch_size=50 plus saveAll() lets JPA batch inserts instead of issuing one per entity.

Beginner mistake

Calling repository.save(entity) inside a for-loop in Spring Data JPA — this issues one INSERT (and often one extra SELECT for ID generation strategy checks) per entity, exactly the anti-pattern this section fixes.

07 · Anti-pattern

SELECT * Problems

The most common query smell in every fresher's first codebase — convenient to write, quietly expensive at scale.

ProblemWhy it hurts
Wider network payloadPulls every column, including large TEXT/BLOB fields you don't need, over the wire
Disables covering indexesA covering index only helps if the query's needed columns fit inside it — SELECT * almost always forces a trip back to the full table row
Breaks silently on schema changesAdding a column changes what * returns, potentially breaking code relying on positional column order
Over-fetches for the use caseAn API that only needs id + name still deserializes every column into memory, then discards most of it
select_star.sql
-- Anti-pattern
SELECT * FROM employees WHERE dept_id = 2;

-- Fixed: only the columns the API/view actually needs
SELECT id, first_name, email FROM employees WHERE dept_id = 2;
→ Narrower SELECT list can turn a non-covering index lookup into a fully covering one — visible as "Using index" appearing in EXPLAIN's Extra column
Interview tip

This connects directly back to Module 4's naming-columns-explicitly rule for INSERT — the same "name what you need explicitly" discipline applies on the read side for the same reasons: clarity, resilience to schema change, and performance.

Best practice

In Spring Data JPA, use projections (interface-based or DTO constructor expressions) instead of fetching full entities when an endpoint only needs a subset of fields — this is the Java-side equivalent of avoiding SELECT *.

01Interview questions

Asked at TCS Digital: Why is SELECT * considered bad practice in production code? TCS Digital+

It over-fetches unnecessary columns (network + memory cost), can prevent covering-index optimizations, and silently changes behavior when the schema evolves — naming explicit columns is safer, faster, and more self-documenting.

Revision

Cheat Sheet

EXPLAIN

Check type (avoid ALL), key (index used), rows, and Extra before trusting any query is fast.

Slow Queries

Enable the slow query log; rank by frequency × duration, not just single-query time.

Index Optimization

Leftmost-prefix rule for composite indexes; covering indexes skip the table lookup entirely.

Query Optimization

Keep conditions sargable — never wrap an indexed column in a function.

Pagination

Keyset (seek) pagination beats OFFSET at depth — constant time vs linear scan-and-discard.

Batch Insert

One multi-row INSERT beats thousands of single-row round trips.

SELECT *

Name only the columns you need — for network cost, index coverage, and schema resilience.
