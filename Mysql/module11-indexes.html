Indexes — The Book's Table of Contents

Without an index, MySQL reads every single row to answer your query — a full table scan. An index is a pre-sorted side structure that lets it jump straight to the rows that matter, the way a book's index sends you to a page instead of making you read cover to cover.

1,000,000 rows, no index:
SELECT * FROM employees WHERE email = 'raj@x.com';
-- scans all 1,000,000 rows
Add INDEX(email) and MySQL walks a B+ Tree in roughly log₂(1,000,000) ≈ 20 steps to find the row — the difference between reading a phone book cover-to-cover and looking up a name alphabetically.
01

Why Indexes Exist

A table with no index forces MySQL into a full table scan for almost every WHERE, JOIN, or ORDER BY — reading every row just to check if it matches. An index trades a bit of extra storage and slower writes for dramatically faster reads.

Problem it solves

Slow lookups

Finding one row among millions without an index means reading all of them.

Slow sorting

ORDER BY on an unindexed column means sorting the entire result set in memory or on disk.

Slow joins

Joining two tables on unindexed columns forces MySQL into nested-loop scans of both sides.

Real-world example

A login query — WHERE email = ? — runs on every single request. On a 5-million-row users table with no index on email, that's a full scan per login attempt. One index turns it into a near-instant B+ Tree lookup.

Interview one-liner

"An index is a separate, sorted data structure that maps column values to row locations, so MySQL can find matching rows without scanning the whole table."

02

B+ Tree — How MySQL Actually Stores an Index

InnoDB (MySQL's default engine) implements every index as a B+ Tree: a balanced, sorted tree where all actual data lives only in the leaf nodes, and leaf nodes are linked together in a chain for fast range scans.

Why B+ Tree, not a plain sorted array or hash?

vs Sorted Array

Inserts/deletes in a sorted array are O(n) (shift everything). B+ Tree keeps inserts/deletes near O(log n) by rebalancing locally.

vs Hash Index

A hash index gives O(1) equality lookups but can't do range queries (>, <, BETWEEN) or ORDER BY — B+ Tree can, because it stays sorted.

Shallow & wide

Each node holds many keys, so the tree stays only 3–4 levels deep even for millions of rows — very few disk reads per lookup.

Interview trap

"Why not a binary tree?" — A binary tree has only 2 children per node, so it grows too tall for millions of rows (more disk reads). A B+ Tree node holds hundreds of keys, keeping the tree shallow and disk-I/O-friendly.

03

Clustered Index (Concept)

In InnoDB, the table's actual row data is physically stored inside the leaf nodes of one special B+ Tree — the clustered index. There is exactly one per table, and every table effectively is its clustered index.

Which column becomes the clustered index?

  1. The PRIMARY KEY, if one is defined.
  2. Otherwise, the first UNIQUE NOT NULL column.
  3. Otherwise, InnoDB silently generates a hidden 6-byte row ID (ROW_ID) and clusters on that.
Interview one-liner

"The clustered index isn't a separate structure next to the table — for InnoDB, the table IS the clustered index. That's why every InnoDB table should have a well-chosen primary key."

Why primary key choice matters

Rows are physically stored in primary key order. A random primary key (like a UUID) causes constant page splits and fragmentation as new rows insert into the middle of the tree — an auto-increment integer keeps inserts sequential and fast.

04

Secondary Index

Any index that isn't the clustered index. Its leaf nodes don't store full rows — they store the indexed column's value plus the primary key value of the matching row.

CREATE INDEX idx_email ON employees(email);

This two-step hop (secondary index → primary key → clustered index) is called a bookmark lookup. It's exactly what a covering index (below) is designed to avoid.

Beginner mistake

Assuming a secondary index stores the whole row. It only stores the indexed column(s) plus the primary key — MySQL must do a second lookup into the clustered index for any other column you SELECT.

05

Composite Index (Multi-Column)

An index built on more than one column, sorted by the first column, then the second within each first-column group, and so on — like sorting a phonebook by last name, then first name.

CREATE INDEX idx_dept_salary ON employees(dept_id, salary);

Leftmost Prefix Rule

MySQL can use a composite index only if the query filters on a leftmost, unbroken prefix of its columns.

✓ Can use idx_dept_salary

WHERE dept_id = 3
WHERE dept_id = 3 AND salary > 50000

✗ Cannot use idx_dept_salary

WHERE salary > 50000 (skips dept_id, the leftmost column)

Very frequently asked

"Order of columns in a composite index — does it matter?" — Yes, critically. Put the column used for equality (=) first, and the column used for range (>, <, BETWEEN) last, since a range condition stops the leftmost-prefix match for any columns after it.

06

Covering Index

An index "covers" a query when every column the query needs — in SELECT, WHERE, and ORDER BY — exists inside the index itself. MySQL then never touches the clustered index at all.

CREATE INDEX idx_covering ON employees(dept_id, name);

-- fully covered: dept_id and name both live in idx_covering
SELECT name FROM employees WHERE dept_id = 3;

In EXPLAIN, a covering index shows up as Using index in the Extra column — the single strongest sign that a query is well optimized.

Best practice

For hot, repeated read queries (dashboards, login checks), design the index to include every selected column — turning a two-hop bookmark lookup into a single index-only scan.

07

Unique Index

A B+ Tree index that also enforces a constraint: no two rows may share the same (non-NULL) value in the indexed column(s).

CREATE UNIQUE INDEX idx_email_unique ON employees(email);
-- or inline:
ALTER TABLE employees ADD CONSTRAINT uq_email UNIQUE (email);

08

EXPLAIN — Reading the Optimizer's Mind

EXPLAIN shows exactly how MySQL plans to execute a query — which index (if any) it will use, how many rows it expects to examine, and the access strategy.

EXPLAIN SELECT name FROM employees WHERE dept_id = 3;

Key columns to read

type

Access strategy, best → worst: const > eq_ref > ref > range > index > ALL. ALL means a full table scan.

key

Which index MySQL actually chose to use — NULL means no index was used.

rows

Estimated number of rows MySQL expects to examine — lower is better.

Extra

Using index (covering, great) vs Using filesort / Using temporary (red flags worth investigating).

Interview trap

"If a query has a WHERE clause on an indexed column, will MySQL always use the index?" — No. On a small table or when the filter matches a large fraction of rows, the optimizer may choose a full scan because it's estimated to be cheaper than random-access index lookups.

09

Spring Boot Relation

JPA/Hibernate doesn't create useful indexes automatically beyond the primary key — you declare them explicitly, either in the entity or in a migration tool like Flyway/Liquibase.

@Entity
@Table(name = "employees", indexes = {
    @Index(name = "idx_email", columnList = "email", unique = true),
    @Index(name = "idx_dept_salary", columnList = "dept_id, salary")
})
public class Employee { ... }
Interview angle

"Where do you put indexes in a Spring Boot project?" — Prefer a versioned migration (Flyway/Liquibase) over relying on Hibernate's ddl-auto, so index creation is explicit, reviewable, and safe to run in production.

Advantages · Disadvantages · When to Use / Avoid

Advantages

Dramatically faster SELECT, JOIN and ORDER BY · enables efficient range queries · can enforce uniqueness · covering indexes avoid extra I/O entirely.

Disadvantages

Extra disk space per index · every INSERT/UPDATE/DELETE must also update every index on that table · too many indexes slow writes and confuse the optimizer's choice.

When to use

Columns in WHERE/JOIN/ORDER BY that are frequently queried, especially on large tables with selective (high-cardinality) values.

When NOT to use

Tiny tables (scan is already fast) · low-cardinality columns like a boolean flag alone · columns rarely used in filters · write-heavy tables where index maintenance cost outweighs read benefit.

12

Performance Notes, Beginner Mistakes & Best Practices

Performance note

Every index you add speeds up reads but slows down writes — each INSERT/UPDATE/DELETE has to maintain every index's B+ Tree, not just the table itself.

Beginner mistake

Wrapping an indexed column in a function in WHERE — e.g. WHERE YEAR(hire_date) = 2024 — makes the index unusable, since MySQL can't look up a computed value in the sorted tree. Rewrite as a range: WHERE hire_date >= '2024-01-01' AND hire_date < '2025-01-01'.

Beginner mistake

Indexing every column "just in case." Low-cardinality columns (like a gender or status flag with 2-3 values) rarely help, since the index doesn't narrow the search much.

Best practice

Index columns that are actually filtered/joined/sorted on in production queries — verify with EXPLAIN and slow query logs, not guesswork.

Interview, Scenario & Company Questions

How many clustered indexes can a table have?+
Exactly one — because it defines the physical row order on disk, a table can't be sorted two ways at once.
Why does an auto-increment primary key perform better than a random UUID as clustered key?+
Sequential inserts append to the end of the B+ Tree; random UUIDs insert into random positions, causing frequent page splits and fragmentation.
What's a bookmark lookup?+
The second step where MySQL takes the primary key found in a secondary index and looks it up in the clustered index to fetch remaining columns.
A query filters on (last_name, first_name) but you only have an index on first_name. Slow or fast?+
Slow — the existing index doesn't match the filter's leading column. Create a composite index with last_name first (assuming it's the equality/more selective filter), then first_name.
EXPLAIN shows "Using filesort" on an ORDER BY query. What do you do?+
Add or extend an index so its column order matches the ORDER BY clause, letting MySQL read rows already in sorted order instead of sorting them after fetching.

ZohoTCS DigitalInfosysAccentureCapgeminiCognizantHCLWipro

[Zoho / Product companies] How would you design indexes for a table with 50M rows and heavy writes?+
Index only the columns actually used in hot query filters/joins/sorts, prefer a sequential primary key, and monitor with EXPLAIN + slow query log rather than indexing preemptively.
[TCS Digital / Infosys] What is the difference between a clustered and non-clustered index?+
Clustered: leaf nodes store the actual row data, physical row order = index order, one per table. Non-clustered (secondary): leaf nodes store the key plus a pointer (primary key) to the row, many allowed per table.
[Accenture / Capgemini / Cognizant] Does adding more indexes always improve performance?+
No — a very common trap question. More indexes speed reads but slow every write, and an unused index is pure overhead. Index deliberately, not exhaustively.

Memory Tricks

"Clustered = Contains"

Clustered index leaf Contains the full row. Secondary leaf just Contains a pointer.

Leftmost like a phonebook

Composite index = sorted by last name, then first name. You can't jump to "first name starts with R" without knowing the last name first.

"Covering = no crossing"

A covering index means MySQL never has to cross over into the clustered index for extra columns.

Summary

Indexes are B+ Trees that trade write cost and storage for dramatically faster reads. InnoDB clusters table data with the primary key; every other index is secondary and requires a bookmark lookup unless it's covering. Composite indexes obey the leftmost prefix rule — column order matters. EXPLAIN is how you verify, never assume, that an index is actually being used.

Revision Notes

  • B+ Tree: sorted, balanced, shallow, leaf nodes linked for range scans
  • Clustered = one per table = physical row storage (usually the PK)
  • Secondary = key + PK pointer → bookmark lookup into clustered index
  • Composite index: leftmost prefix rule; equality columns first, range columns last
  • Covering index: query fully answered from the index, no bookmark lookup ("Using index" in EXPLAIN)
  • Unique index: enforces no duplicates; multiple NULLs allowed
  • EXPLAIN: check type, key, rows, and Extra before trusting a query is optimized
