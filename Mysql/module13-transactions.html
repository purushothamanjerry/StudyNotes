What Is a Transaction

A transaction is a sequence of one or more SQL statements executed as a single, indivisible logical unit of work.

Why this exists

  • Some real-world operations are only meaningful if every step succeeds together — a bank transfer isn't "half done" safely.
  • Without transactions, a crash or error midway through a multi-step operation could leave data in a broken, inconsistent state.
  • Transactions give MySQL a way to guarantee: either every statement in the group takes effect, or none of them do.

Simple vs Interview Explanation

Simple Explanation

A transaction is like a "save point" for a group of database changes — you can either keep all of them or throw all of them away.

Interview Explanation

"A transaction is a logical unit of work bounded by START TRANSACTION and either COMMIT or ROLLBACK, guaranteeing the ACID properties for every statement inside it."

Interview Tip

This is consistently rated one of the highest-frequency topics in fresher Java Backend interviews, because it connects SQL directly to Spring's @Transactional — expect at least one question on it in almost every product-company interview.

02

ACID Properties

The four guarantees every transaction must satisfy — the theoretical backbone of this entire module.

A
Atomicity

All statements succeed, or none do — no partial transactions.

C
Consistency

A transaction moves the database from one valid state to another, never violating constraints.

I
Isolation

Concurrent transactions don't see each other's uncommitted changes.

D
Durability

Once committed, changes survive crashes, power loss, and restarts.

PropertyBank Transfer Analogy
AtomicityDebit ₹500 from A and credit ₹500 to B happen together, or neither happens.
ConsistencyTotal money across both accounts is the same before and after — no money is created or destroyed.
IsolationAnother customer checking their balance mid-transfer never sees the "half-transferred" state.
DurabilityOnce the bank confirms "transfer successful," it stays successful even if the server crashes a second later.
Common Mistake

Confusing Consistency with Isolation. Consistency is about constraints/business rules always holding true; Isolation is about concurrent transactions not interfering with each other. They sound similar but answer completely different questions.

03

COMMIT

Makes every change made during the current transaction permanent and visible to all other connections.

commit_example.sql
START TRANSACTION;
UPDATE account SET balance = balance - 500 WHERE id = 1;
UPDATE account SET balance = balance + 500 WHERE id = 2;
COMMIT;  -- both updates are now permanent and durable
How MySQL Internally Works

InnoDB writes changes to its redo log as the transaction proceeds; COMMIT flushes that log to disk and marks the transaction complete, which is what actually provides Durability.

04

ROLLBACK

Undoes every change made since the transaction started (or since a named SAVEPOINT).

rollback_example.sql
START TRANSACTION;
UPDATE account SET balance = balance - 500 WHERE id = 1;
-- something goes wrong here...
ROLLBACK;  -- the debit above is completely undone
Warning

ROLLBACK cannot undo DDL statements (CREATE, ALTER, DROP) — those implicitly commit as soon as they run, even inside an otherwise-open transaction.

05

SAVEPOINT

A named checkpoint inside a transaction, letting you roll back part of the work without discarding everything.

savepoint_example.sql
START TRANSACTION;

UPDATE account SET balance = balance - 500 WHERE id = 1;
SAVEPOINT after_debit;

UPDATE account SET balance = balance + 500 WHERE id = 999; -- wrong account!

ROLLBACK TO after_debit;  -- undoes only the bad credit, keeps the debit

UPDATE account SET balance = balance + 500 WHERE id = 2;  -- correct account
COMMIT;
Interview Tip

ROLLBACK TO savepoint_name keeps the transaction open — only a plain ROLLBACK (no savepoint) ends the transaction entirely. Freshers often assume any ROLLBACK closes the transaction.

06

AUTOCOMMIT

MySQL's default mode, where every single SQL statement is treated as its own complete transaction and committed immediately.

autocommit_example.sql
SELECT @@autocommit;  -- 1 by default

SET autocommit = 0;
UPDATE account SET balance = balance - 500 WHERE id = 1;
-- change is NOT visible to other connections yet
COMMIT;  -- now it is
Common Mistake

Forgetting that START TRANSACTION temporarily suspends autocommit for that block regardless of the session's autocommit setting — you don't need to manually disable autocommit if you always wrap multi-statement work in an explicit transaction.

08

Common Mistakes & Performance Notes

Assuming ROLLBACK can undo DDL ▾
CREATE, ALTER, DROP, and TRUNCATE all implicitly commit — a ROLLBACK afterward has no effect on them, only on DML statements around them.
Leaving transactions open too long ▾
Long-running open transactions hold locks and prevent InnoDB from purging old row versions, bloating tablespace and blocking other queries — always commit or rollback promptly.
Confusing ROLLBACK with ROLLBACK TO SAVEPOINT ▾
A plain ROLLBACK ends the transaction entirely; ROLLBACK TO a savepoint only undoes work after that point and keeps the transaction open for more statements.
Forgetting that MyISAM doesn't support transactions ▾
START TRANSACTION / COMMIT / ROLLBACK are silently no-ops on MyISAM tables — transactional guarantees require InnoDB.

Spring Boot Relation

This is the module where SQL theory and everyday Spring Boot code meet most directly.

TransferService.java
@Service
public class TransferService {

    @Transactional
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        accountRepo.debit(fromId, amount);
        accountRepo.credit(toId, amount);
        // if credit() throws, Spring auto-rolls back the debit too
    }
}
SQL ConceptSpring Boot Equivalent
START TRANSACTION@Transactional begins a transaction when the method is entered
COMMITHappens automatically when the method returns normally
ROLLBACKHappens automatically on an unchecked (RuntimeException) exception by default
SAVEPOINTAchievable with nested @Transactional(propagation = Propagation.NESTED)
Isolation level@Transactional(isolation = Isolation.READ_COMMITTED) etc.
Classic Interview Trap

By default, @Transactional only rolls back on unchecked exceptions — a checked exception will NOT trigger a rollback unless you explicitly add rollbackFor = Exception.class. This single fact is asked constantly.

10

Isolation Levels — A Preview

Isolation (the "I" in ACID) has degrees — MySQL's default isn't the only option. This is a light preview; the full deep-dive is a later module.

Isolation LevelTrade-off
READ UNCOMMITTEDFastest, but allows dirty reads (seeing uncommitted changes from others)
READ COMMITTEDNo dirty reads, but non-repeatable reads are still possible
REPEATABLE READ (MySQL default)No dirty or non-repeatable reads; phantom reads still possible in theory, though InnoDB largely prevents them via MVCC
SERIALIZABLEStrongest guarantee, but the slowest — transactions effectively run one at a time
Interview Tip

Freshers are rarely asked to explain MVCC in depth, but knowing that MySQL's default isolation level is REPEATABLE READ (unlike many other databases that default to READ COMMITTED) is a very common one-line fact question.

Memory Tricks

ACID

"A Cat Ignores Dogs" → Atomicity, Consistency, Isolation, Durability.

COMMIT vs ROLLBACK

"COMMIT keeps, ROLLBACK erases" — think of COMMIT as saving a document, ROLLBACK as closing it without saving.

SAVEPOINT

"A checkpoint in a video game" — you don't restart the whole level, just go back to the last checkpoint.

SQL Practice Questions

Write a transaction that transfers ₹2,000 from account 5 to account 8, rolling back if account 5's balance would go negative ▾
START TRANSACTION;
UPDATE account SET balance = balance - 2000 WHERE id = 5;

SELECT balance FROM account WHERE id = 5 INTO @bal;

SET @bal = (SELECT balance FROM account WHERE id=5);
UPDATE account SET balance = balance + 2000 WHERE id = 8;

-- application/procedure layer checks @bal >= 0, then:
COMMIT;   -- or ROLLBACK; if @bal was negative
Use a SAVEPOINT to safely retry only the second of two updates ▾
START TRANSACTION;
UPDATE inventory SET stock = stock - 1 WHERE product_id = 10;
SAVEPOINT before_log;
INSERT INTO audit_log (msg) VALUES ('stock updated');
ROLLBACK TO before_log;  -- undo just the log insert if it fails validation
COMMIT;
Check the current autocommit setting and temporarily disable it ▾
SELECT @@autocommit;
SET autocommit = 0;

Summary

A transaction groups one or more statements into a single all-or-nothing unit of work, guaranteed by the four ACID properties: Atomicity, Consistency, Isolation, and Durability. COMMIT makes changes permanent; ROLLBACK undoes them entirely; SAVEPOINT allows a partial rollback without discarding the whole transaction; and AUTOCOMMIT is MySQL's default mode of treating every statement as its own tiny transaction unless you explicitly start one yourself. The bank transfer example is the canonical illustration of why all of this matters — and it's exactly the pattern Spring's @Transactional automates in real applications.
