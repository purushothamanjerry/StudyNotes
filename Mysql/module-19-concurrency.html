Concurrency

A single-user query is easy. The real world has two checkout requests hitting the same seat at the same millisecond. This module covers what happens when multiple transactions touch the same row simultaneously — and how MySQL, and your Spring Boot service layer, keep that safe.

⭐ Why this module is the capstone

Correct SQL isn't enough under concurrent load

Every query you've written in this track has been analyzed as if it ran alone. Production systems never work that way — dozens of Spring Boot request threads can hit the same row within milliseconds of each other. Concurrency is where "works on my machine" meets "loses money in production."

Real-world analogy

Two people looking at the same bank balance on two different ATMs at the exact same second, both withdrawing money based on what they saw — if the system isn't careful, one withdrawal can silently overwrite the effect of the other.

Interview framing

Interviewers ask concurrency questions specifically to see if you think about multi-user reality, not just single-request correctness — a strong differentiator even among freshers.

01 · Concept

Race Condition

When the correctness of a result depends on the unpredictable timing of two or more operations racing against each other.

race_condition.sql
-- Classic "check-then-act" race: verify stock, then decrement, as TWO steps
SELECT stock FROM products WHERE id = 42;  -- app reads: stock = 1
-- app logic: "if stock > 0, allow purchase" ... then, separately:
UPDATE products SET stock = stock - 1 WHERE id = 42;
→ If two customers both read stock=1 before either UPDATE runs, both purchases can succeed — selling one item twice
Customer A (Java thread 1)
t=0ms — SELECT stock → sees 1
t=15ms — app: "stock > 0, proceed"
t=20ms — UPDATE stock = stock - 1
Customer B (Java thread 2)
t=5ms — SELECT stock → also sees 1
t=18ms — app: "stock > 0, proceed"
t=25ms — UPDATE stock = stock - 1 → sold twice, stock now -1 or overwritten
Interview trap

This exact "check stock, then update" pattern is the #1 asked concurrency scenario. The fix isn't application-level logic speed — it's making the check-and-decrement atomic at the database level: UPDATE products SET stock = stock - 1 WHERE id = 42 AND stock > 0; and checking the affected row count.

01Interview questions

Asked at Zoho: How do you prevent overselling the last item in stock under concurrent requests? Zoho+

Combine the check and the decrement into one atomic UPDATE statement with the condition in WHERE: UPDATE products SET stock = stock - 1 WHERE id = ? AND stock > 0, then check if the affected row count is 1 (success) or 0 (already sold out) — no separate SELECT-then-UPDATE race window exists.

02 · Anomaly

Lost Update

A specific, extremely common race condition outcome: two transactions read the same value, both compute a new value from it, and the second write silently erases the first.

lost_update.sql
-- Txn A and Txn B both read balance = 1000 at nearly the same time
-- Txn A: deduct 100
UPDATE accounts SET balance = 1000 - 100 WHERE id = 7; -- writes 900
-- Txn B: deduct 50, computed from the SAME stale read of 1000
UPDATE accounts SET balance = 1000 - 50  WHERE id = 7; -- writes 950, overwriting A's 900
→ Final balance is 950, not the correct 850 — Txn A's ₹100 deduction was completely lost
Txn A — deduct ₹100
READ balance = 1000
WRITE balance = 900
Txn B — deduct ₹50
READ balance = 1000 (before A's write)
WRITE balance = 950 → A's update is gone
Beginner mistake

Reading a value in Java (Account account = repo.findById(id)), modifying it in memory (account.setBalance(account.getBalance() - 100)), then calling save() — this "read, modify in app, write back" pattern is exactly how lost updates happen when two requests interleave.

Best practice

Prefer a single atomic UPDATE accounts SET balance = balance - 100 WHERE id = 7 (letting MySQL compute from the current row value) over read-modify-write in application code whenever possible — or use locking (covered next) when app-level logic between read and write is unavoidable.

01Interview questions

What's the difference between a race condition and a lost update?+

A race condition is the general category — any outcome depending on unpredictable timing between concurrent operations. A lost update is a specific, very common race condition outcome where one transaction's write is silently overwritten by another's, based on both having read the same stale value.

03 · Concept

MVCC (concept)

Multi-Version Concurrency Control — how InnoDB lets readers and writers work on the same row simultaneously without blocking each other, most of the time.

01The core idea

Instead of readers waiting for writers to finish, InnoDB keeps multiple "snapshot" versions of a row. When Transaction A starts, it sees a consistent snapshot of the data as of that moment — even if Transaction B commits a change to the same row a moment later, A keeps seeing its own snapshot until it re-reads or commits (depending on isolation level).

1

A row is updated

InnoDB doesn't overwrite the old version in place — it keeps the old version accessible via the undo log, and marks the new version with the updating transaction's ID.

2

Readers see a consistent snapshot

A SELECT running concurrently reads the version of the row that was committed at (or before) its own transaction's start point — never a half-written or uncommitted value.

3

Readers don't block writers, and vice versa

Because there's no need to wait for a lock just to read a consistent snapshot, MVCC gives huge concurrency gains over lock-everything approaches — this is why plain SELECTs in InnoDB normally don't block on writes.

4

Old versions are cleaned up later

Once no active transaction still needs an old row version, InnoDB's purge process reclaims that undo log space.

Interview tip

The one-liner to say: "MVCC is why readers don't block writers and writers don't block readers in InnoDB — each transaction sees a consistent snapshot instead of fighting over locks just to read." This directly explains why MySQL performs well under mixed read/write load compared to naive full-table locking.

Interview trap

MVCC handles concurrent reads gracefully — it does not by itself prevent lost updates between two concurrent writers. Two transactions can each read their own consistent snapshot and still both attempt conflicting writes; that's exactly what locking (next two sections) exists to resolve.

02Interview questions

Why don't plain SELECT queries usually get blocked by concurrent UPDATEs in InnoDB?+

Because of MVCC — a SELECT reads a consistent snapshot version of the row from the undo log rather than needing to acquire a lock on the current, possibly-being-modified row.

04 · Strategy

Optimistic Locking

Assume conflicts are rare: let everyone read and modify freely, but detect and reject a conflicting write at the last moment using a version check.

optimistic_locking.sql
-- Table has a version column
SELECT balance, version FROM accounts WHERE id = 7; -- balance=1000, version=5

-- Update only succeeds if version hasn't changed since we read it
UPDATE accounts
SET balance = 900, version = version + 1
WHERE id = 7 AND version = 5;
-- affected rows = 0 means someone else updated it first -- retry or fail
→ If another transaction already bumped version to 6, this UPDATE matches zero rows — the app detects the conflict via affected-row count and can retry or surface an error

01Spring Boot / JPA relation

Account.java
@Entity
public class Account {
    @Id private Long id;
    private BigDecimal balance;

    @Version
    private Long version; // Hibernate manages this automatically
}
// A conflicting concurrent save() throws OptimisticLockException automatically
Interview tip

Hibernate's @Version annotation implements exactly this pattern under the hood — it adds the version column to every UPDATE's WHERE clause and throws OptimisticLockException when zero rows are affected.

When to use it

High-read, low-conflict scenarios — most web form edits, profile updates, catalog management — where two people rarely edit the exact same row at the exact same second, so the retry/failure path is rare and cheap.

02Interview questions

Scenario: Two admins edit the same product listing at once with optimistic locking enabled. What happens? Scenario+

Both read version=5. The first save succeeds and bumps it to 6. The second save's WHERE version=5 matches zero rows, so Hibernate throws OptimisticLockException — the second admin's UI should catch this, refresh the latest data, and prompt them to re-apply or merge their changes.

05 · Strategy

Pessimistic Locking

Assume conflicts are likely: lock the row up front so no other transaction can touch it until you're done.

pessimistic_locking.sql
START TRANSACTION;
SELECT balance FROM accounts WHERE id = 7 FOR UPDATE; -- locks this row
-- any other transaction's SELECT ... FOR UPDATE on id=7 now BLOCKS and waits
UPDATE accounts SET balance = balance - 100 WHERE id = 7;
COMMIT; -- lock released here
→ Txn B's SELECT ... FOR UPDATE on the same row waits until Txn A commits or rolls back — no interleaving is possible
Txn A
SELECT ... FOR UPDATE → row locked
UPDATE balance - 100
COMMIT → lock released
Txn B
SELECT ... FOR UPDATE → BLOCKED, waiting...
(still waiting on A's lock)
Lock acquired now — sees A's committed balance
AspectOptimisticPessimistic
ApproachDetect conflict at write timePrevent conflict up front with a lock
ConcurrencyHigher — no blocking on readLower — other transactions wait
Best forLow-contention, high-read scenariosHigh-contention, must-not-fail scenarios (e.g. seat booking, inventory decrement)
Failure modeConflict detected after work is done — must retryRisk of deadlocks/timeouts if locks held too long
JPA annotation@Version@Lock(LockModeType.PESSIMISTIC_WRITE)
Interview trap

Holding a pessimistic lock for too long (e.g. across a slow external API call inside the same transaction) is a common way to accidentally cause lock timeouts and deadlocks in production — keep locked transactions as short as possible.

01Interview questions

Asked at Capgemini: When would you choose pessimistic over optimistic locking? Capgemini+

When conflicts are frequent and expensive to retry — like the very last seat in a flight booking system, where you'd rather make the second customer briefly wait than let both "succeed" and then have to reconcile an overbooking after the fact.

06 · Applied

Spring @Transactional

The annotation that ties everything in this module together in a real Java backend — where transaction boundaries actually live in application code.

AccountService.java
@Service
public class AccountService {

    @Transactional
    public void transferMoney(Long fromId, Long toId, BigDecimal amount) {
        Account from = accountRepo.findById(fromId);
        Account to   = accountRepo.findById(toId);
        from.debit(amount);
        to.credit(amount);
        // both writes commit together, or neither does
    }
}
→ If credit() throws after debit() succeeds, Spring rolls back the ENTIRE method — the debit is undone too, so money is never silently lost from one account without appearing in the other

01What @Transactional actually does

1

Spring wraps the method in a proxy

A dynamic proxy intercepts the call, starts a database transaction before your method body runs.

2

All DB operations inside share one transaction

Every repository call inside the method participates in the same underlying JDBC transaction/connection.

3

Success → COMMIT; unchecked exception → ROLLBACK

By default, Spring rolls back only on RuntimeException/unchecked exceptions — checked exceptions do NOT trigger a rollback unless explicitly configured with rollbackFor.

Interview trap — the #1 asked @Transactional gotcha

Self-invocation doesn't trigger the proxy. If method A (not annotated) calls method B (annotated @Transactional) on the same class instance via this.methodB(), Spring's proxy is bypassed entirely and no transaction is started. @Transactional only works through the Spring-managed proxy, which requires an external call through the bean.

Beginner mistake

Assuming @Transactional rolls back on any exception. By default it only rolls back on unchecked (RuntimeException and Error) exceptions — a checked exception silently commits unless you specify @Transactional(rollbackFor = Exception.class).

02Isolation levels, briefly

Isolation LevelPreventsAllows
READ UNCOMMITTEDNothingDirty reads, non-repeatable reads, phantom reads
READ COMMITTEDDirty readsNon-repeatable reads, phantom reads
REPEATABLE READ (MySQL default)Dirty + non-repeatable readsPhantom reads (largely mitigated by MVCC + gap locks in InnoDB)
SERIALIZABLEAll of the aboveNothing — full isolation, lowest concurrency
Interview tip

MySQL's InnoDB default isolation level is REPEATABLE READ — different from many other databases (like PostgreSQL/Oracle, which default to READ COMMITTED). This is a frequently asked "gotcha" fact.

03Interview questions

Asked at Cognizant: Why doesn't @Transactional work when a method calls another @Transactional method on itself? Cognizant+

Spring implements @Transactional using a proxy around the bean. A call like this.otherMethod() bypasses the proxy entirely since it's a direct internal Java call, not a call through the Spring-managed bean reference — so no new transaction is started for that inner call.

Scenario: Your @Transactional method catches an exception internally and logs it instead of rethrowing. Does the transaction still roll back? Scenario+

No — if the exception is caught and swallowed inside the method, Spring's proxy never sees it, so the transaction commits normally (potentially with partial/incorrect state). Rollback only triggers when a qualifying exception actually propagates out of the method.

Cheat Sheet

Race Condition

Outcome depends on unpredictable timing between concurrent operations — fix by making check-and-act atomic.

Lost Update

Two writers overwrite each other based on the same stale read — fix with a single atomic UPDATE or a version check.

MVCC

Readers see consistent snapshots without blocking writers — InnoDB's default concurrency mechanism.

Optimistic Locking

Version column checked at write time; @Version in JPA; best for low-contention scenarios.

Pessimistic Locking

SELECT ... FOR UPDATE locks the row up front; best for high-contention, must-not-fail scenarios.

@Transactional

Proxy-based; rolls back on unchecked exceptions by default; self-invocation bypasses it entirely.

Summary & Revision Notes

Race Condition

Outcome depends on operation timing — fix with atomicity, not "faster" application code.

Lost Update

Stale-read-then-overwrite; fix with atomic UPDATEs or version checks.

MVCC

Consistent snapshots let readers avoid blocking writers — InnoDB's default concurrency engine.

Optimistic Locking

Detect conflicts at write time via a version column — low overhead, best for rare contention.
