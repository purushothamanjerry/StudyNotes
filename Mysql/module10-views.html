Views — Virtual Windows Into Your Data

A VIEW never stores rows. It stores a question. Every time someone looks through it, MySQL re-asks that question against the real tables and hands back the answer — like a pane of glass shaped to show exactly what you're allowed to see.

Base table: employees(id, name, salary, dept_id, ssn)
CREATE VIEW public_employees AS
SELECT id, name, dept_id
FROM employees;
The view exposes only id, name, dept_id — salary and ssn stay hidden. No copy of data is made. Query the view, and MySQL quietly rewrites it into a query against employees at execution time.
01

Introduction & Why Views Exist

A VIEW is a named, saved SELECT query that behaves like a virtual table. It has rows and columns like a table, you can query it like a table — but it holds no data of its own.

Why this topic exists

Real schemas get messy: five-table joins, repeated filters, sensitive columns mixed with public ones. Views exist to give people a clean, safe, reusable name for a complicated or restricted question, instead of forcing everyone to rewrite (and re-secure) that same query by hand.

Problem it solves

Repetition

The same 4-table JOIN written in 10 different reports becomes one view, queried 10 times.

Exposure

Junior staff need employee names and departments, never salary or SSN. A view hides the columns entirely.

Complexity

Analysts who don't know SQL joins can query a simple view name instead of a five-table statement.

Real-world example

Think of a company directory app on the intranet. HR's database has full salary and tax details. The directory app's login only needs name, designation and department. Instead of trusting every app query to "remember" not to select salary, DBAs create employee_directory_view and grant the app access to only that — the sensitive columns are structurally unreachable, not just conventionally avoided.

Interview one-liner

"A view is a stored SELECT statement with a name. It has no storage of its own — it's a lens on the base tables, evaluated fresh on every query."

02

Simple vs Deep Explanation

A view is a saved query with a name. SELECT * FROM my_view; runs the query stored inside the view, every single time — it never returns "old" or "cached" data unless you explicitly ask MySQL to materialize it.

MySQL stores the view's definition (its SQL text) in the information_schema.VIEWS table and as a .frm-equivalent metadata entry in the data dictionary. No rows are written to disk for the view itself. When a query references the view, MySQL's optimizer either merges the view's SQL into the outer query (MERGE algorithm) or runs the view as an independent derived table first and queries that result (TEMPTABLE algorithm).

A view is like a tinted car window. The world outside (the base table) doesn't change. But depending on the tint (the view's SELECT + WHERE), you only see part of it, from a fixed angle, in a fixed color. Move the actual world (UPDATE the base table) and the window updates instantly — because it was never a photograph, only glass.

04

Step-by-Step Flow & How MySQL Internally Works

  1. Client sends SELECT * FROM public_employees WHERE dept_id = 3;
  2. Parser resolves public_employees as a VIEW, fetches its stored definition from the data dictionary.
  3. Optimizer decides the algorithm: MERGE (rewrite the outer query, folding the view's SELECT and WHERE into one combined query against employees) or TEMPTABLE (run the view's SELECT first into an internal temp table, then run the outer query against that temp table).
  4. MERGE is preferred when possible — it's a rewrite, not a materialization, so indexes on the base table are still usable and it's usually faster.
  5. TEMPTABLE is forced when the view contains: DISTINCT, GROUP BY, UNION, aggregate functions, subqueries in the SELECT list, or no one-to-one row mapping to the base table.
  6. Result rows are streamed back as if public_employees were a real table.
Interview trap

Interviewers love asking: "Does a view store data?" The correct, precise answer is no — unless you explicitly force materialization by copying it into a real table (MySQL has no native MATERIALIZED VIEW keyword, unlike Oracle/PostgreSQL).

05

Create View

Basic syntax, with optional algorithm and security clauses:

CREATE [OR REPLACE]
    [ALGORITHM = {UNDEFINED | MERGE | TEMPTABLE}]
    [DEFINER = user]
    [SQL SECURITY {DEFINER | INVOKER}]
VIEW view_name [(column_list)]
AS select_statement
[WITH [CASCADED | LOCAL] CHECK OPTION];

Example

CREATE OR REPLACE VIEW high_earners AS
SELECT id, name, dept_id, salary
FROM employees
WHERE salary > 80000;

-- query it exactly like a table
SELECT * FROM high_earners ORDER BY salary DESC;
Common interview follow-up

"Can a view be built on another view?" — Yes. MySQL allows views on views, but each layer adds resolution overhead and makes the MERGE algorithm less likely to apply, so deep view-on-view chains hurt performance.

06

Update View (Updatable Views & WITH CHECK OPTION)

Two different meanings of "update a view" come up in interviews — don't mix them up:

1. Redefining the view

Change what the view's query does, using CREATE OR REPLACE VIEW or ALTER VIEW.

ALTER VIEW high_earners AS
SELECT id, name, salary
FROM employees
WHERE salary > 100000;

2. Writing through the view

Running UPDATE/INSERT/DELETE directly on the view, which MySQL forwards to the base table — only if the view is updatable.

UPDATE high_earners
SET salary = salary * 1.1
WHERE id = 42;

A view is updatable only if it has NO:

Aggregate functions (SUM, COUNT...)GROUP BY / HAVINGDISTINCTUNION / UNION ALLSubquery in SELECT listJoins referencing multiple base tables (partially updatable at best)References to non-updatable views or literal values

WITH CHECK OPTION

Forces every INSERT/UPDATE made through the view to still satisfy the view's own WHERE clause — preventing a row from being written and then immediately vanishing from the view's own result set.

CREATE VIEW senior_staff AS
SELECT * FROM employees WHERE salary > 80000
WITH CHECK OPTION;

-- rejected: 50000 violates the view's own WHERE salary > 80000
INSERT INTO senior_staff (name, salary) VALUES ('Raj', 50000);
Beginner mistake

Assuming every view is updatable. Multi-table joins, GROUP BY summaries, and views with DISTINCT will throw ERROR 1288: The target table is not updatable the moment you try INSERT/UPDATE/DELETE on them.

07

Security

Views are one of the most common ways to implement column-level and row-level access control in MySQL, which has no native row-level security feature.

Column-level security

Grant SELECT on the view only — never on the base table. The app's DB user structurally cannot query salary or ssn because they were never selected into the view.

GRANT SELECT ON mydb.public_employees TO 'app_user'@'%';
-- app_user has NO grant at all on mydb.employees

Row-level security via WHERE

CREATE VIEW my_department_only AS
SELECT * FROM employees
WHERE dept_id = (SELECT dept_id FROM managers WHERE username = CURRENT_USER());

DEFINER vs INVOKER

SQL SECURITY DEFINER (default)

The view runs with the privileges of the user who created it. Useful when you want to grant access through the view without granting access to the base table at all.

SQL SECURITY INVOKER

The view runs with the privileges of the user who is querying it. That user must have their own rights on the underlying base table(s).

Security note

DEFINER views are powerful but dangerous if the definer account is later dropped or its password rotated without updating dependent views — queries against the view then fail with a definer-related privilege error.

08

Spring Boot Relation

In a Spring Boot + JPA/Hibernate backend, a MySQL view is typically mapped like a read-only entity.

@Entity
@Immutable // Hibernate: never attempt INSERT/UPDATE/DELETE on this entity
@Table(name = "public_employees")
public class PublicEmployeeView {
    @Id
    private Long id;
    private String name;
    private Long deptId;
}

The repository interface exposes only findAll() / findById() style read methods — Spring Data won't generate save() calls for an entity marked read-only, matching the fact that the view itself may not be updatable.

Interview angle

"Why map a view instead of writing the JOIN in JPQL every time?" — Same reasoning as raw SQL: the JOIN logic and security boundary live in one place (the database), not scattered across every repository query in the codebase.

10

Advantages · Disadvantages · When to Use / Avoid

Advantages

Simplifies complex joins · enforces column/row-level security · gives a stable interface even if base tables are restructured · encourages reuse instead of copy-pasted SQL · always reflects current data.

Disadvantages

No performance boost by itself (still runs the underlying query) · nested views hurt optimizer clarity · not all views are updatable · adds an extra layer to debug when something looks wrong.

When to use

Repeated complex joins, restricting sensitive columns, giving BI tools a stable read-only schema, simplifying reporting queries for non-SQL-fluent users.

When NOT to use

When you actually need pre-computed speed on a huge aggregation (use a summary table instead) · as a substitute for proper indexing · to "cache" expensive results (a view never caches).

11

Performance Notes, Beginner Mistakes & Best Practices

Performance note

A view is not a performance feature. SELECT * FROM view WHERE x is exactly as expensive as running the view's underlying SQL with that same filter — MySQL does not pre-compute or cache view results.

Beginner mistake

Stacking views 3–4 levels deep ("view of a view of a view") to avoid rewriting SQL. Each layer makes the optimizer's job harder and often forces TEMPTABLE, which is slower than a single flat query.

Best practice

Name views clearly (e.g. vw_public_employees), keep them as flat and simple as possible, avoid SELECT * inside a view definition, and document which base tables/columns each view is protecting.

Interview, Scenario & Company Questions

What happens if the base table is dropped?+
The view definition still exists in the data dictionary, but querying it throws an error (view references a table that doesn't exist) until the base table is recreated or the view is dropped.
Can you create an index on a view?+
No. MySQL views cannot have their own indexes — performance depends entirely on indexes already present on the base tables.
Difference between VIEW and derived table (subquery in FROM)?+
A view is a named, persisted object others can reuse. A derived table is an inline, unnamed subquery that exists only for the lifetime of that one statement.
Your app must never see the "salary" column, but reporting still needs it. How do you design this?+
Create two views: one excluding salary (granted to the app's DB user) and a DEFINER view including salary (granted only to a reporting role). Never grant SELECT on the base table to the app user.
A colleague complains a view-based report is slow. How do you investigate?+
Run EXPLAIN on the query against the view to see whether MERGE or TEMPTABLE is used, check if the underlying base-table columns used in JOIN/WHERE are indexed, and check for unnecessary nested views.

ZohoTCS DigitalInfosysAccentureCapgeminiCognizantHCLWipro

[Zoho / Product companies] Can a view be used to enforce security without touching application code?+
Yes — this is the classic column/row-level security pattern: restrict the DB grant to the view, never the base table, so the boundary is enforced by MySQL itself regardless of what the application does.
[TCS Digital / Infosys / service companies] Is a view faster than a normal query?+
No — this is a very common trick question. A view is exactly as fast (or slow) as the query it wraps; it exists for reuse and security, not speed.
[Accenture / Capgemini / Cognizant] What's the difference between a view and a stored procedure?+
A view is queryable like a table and only wraps a SELECT. A stored procedure is a callable routine that can contain any logic — loops, conditionals, multiple statements, and DML — and is invoked with CALL, not queried.

SQL Practice Questions

1. Write a view that shows only employees hired in the last year.+
Answer
CREATE VIEW recent_hires AS
SELECT id, name, hire_date
FROM employees
WHERE hire_date >= DATE_SUB(CURDATE(), INTERVAL 1 YEAR);
2. Write a view joining employees and departments, showing department name instead of dept_id.+
Answer
CREATE VIEW employee_with_dept AS
SELECT e.id, e.name, d.dept_name
FROM employees e
JOIN departments d ON e.dept_id = d.id;
3. Given "senior_staff" has WITH CHECK OPTION and WHERE salary > 80000, will inserting salary = 60000 through it succeed?+
AnswerNo. WITH CHECK OPTION rejects any row written through the view that wouldn't satisfy the view's own WHERE clause.
4. Drop a view named "high_earners" safely (no error if it doesn't exist).+
Answer
DROP VIEW IF EXISTS high_earners;

Memory Tricks

"VIEW = Virtual"

Both start with a V-sound in meaning: no storage, just a live lens over real tables.

MERGE vs TEMPTABLE

MERGE = "mix into the real query" (fast). TEMPTABLE = "make a Temporary Table first" (slower, needed for GROUP BY/DISTINCT/UNION).

DEFINER vs INVOKER

DEFINER = "the Designer's rights" (creator's privileges). INVOKER = "whoever Invokes it uses their own rights."

Summary

A view is a stored SELECT with a name — no data, always live. Use MERGE-friendly, simple views for performance; expect TEMPTABLE for GROUP BY/DISTINCT/UNION. Updatability has strict rules. DEFINER/INVOKER controls whose privileges apply. Views are MySQL's main tool for column and row-level security since native RLS doesn't exist. They don't improve performance by themselves.

Revision Notes

  • No storage → always current data
  • MERGE (fast, rewrite) vs TEMPTABLE (forced by DISTINCT/GROUP BY/UNION/aggregates)
  • Updatable only if simple: no aggregates, no GROUP BY, no DISTINCT, no UNION, no subquery-in-SELECT
  • WITH CHECK OPTION guards writes made through the view
  • DEFINER (creator's rights) vs INVOKER (caller's rights)
  • No native materialized views in MySQL — simulate with a table + EVENT
