Locks & Deadlocks — Traffic Rules for Concurrent Writers

Isolation levels decide what a transaction is allowed to see. Locks are the actual mechanism that enforces it — the traffic signals that make two transactions take turns instead of colliding on the same row.

Two transactions, one intersection:
-- Txn A
UPDATE accounts SET balance=balance-100 WHERE id=1;
-- row 1 is now X-locked by A

-- Txn B, at the same instant
UPDATE accounts SET balance=balance-50 WHERE id=1;
-- B must WAIT for A's lock to release
B doesn't corrupt A's update — it simply waits. Locks are what turn "same row, same instant" from a race condition into an orderly queue.
01

Why Locks Exist

Multiple transactions can try to read and write the same rows at the same time. Locks are how the database enforces "only one writer at a time on this data" without literally running transactions one after another.

Problem it solves

Lost updates

Two transactions read the same value, both compute a new value from it, and the second write silently overwrites the first.

Write conflicts

Two UPDATEs on the same row at the same instant would corrupt data without a coordination mechanism.

Consistent multi-step operations

A multi-row transfer (debit + credit) needs both rows protected from interference until it fully commits.

Real-world example

Two customers try to buy the last item in stock at the same second. Without locking, both reads could see "1 in stock," both could proceed, and the shop oversells. A row lock on that inventory row forces the second buyer's transaction to wait until the first either commits (stock now 0) or rolls back.

Interview one-liner

"Locks are the concrete mechanism — row-level or table-level — that InnoDB uses to enforce the guarantees promised by the transaction's isolation level."

02

Shared Lock (S) vs Exclusive Lock (X)

InnoDB has exactly two lock "flavors" at the row level, and every locking decision comes down to whether they're compatible.

Shared Lock (S)

Taken for reading. Multiple transactions can hold a shared lock on the same row simultaneously — reading doesn't conflict with other reading.

SELECT * FROM accounts WHERE id=1 LOCK IN SHARE MODE;

Exclusive Lock (X)

Taken for writing. Only one transaction can hold an exclusive lock on a row — and no other transaction can hold any lock (shared or exclusive) on it at the same time.

SELECT * FROM accounts WHERE id=1 FOR UPDATE;
-- UPDATE/DELETE take X locks implicitly

Compatibility Matrix

Another transaction wants SAnother transaction wants X
This transaction holds SCompatible — both proceedBlocked — must wait
This transaction holds XBlocked — must waitBlocked — must wait
Interview one-liner

"Many readers can share a row at once; only one writer can hold it, and a writer locks out readers too — that's the entire shared/exclusive rule."

Visual Diagram — Lock Granularity Spectrum

Finer locks (row-level) allow more concurrency but require careful ordering to avoid deadlocks; coarser locks (table-level) are simpler but serialize far more than necessary.

04

How InnoDB Locking Actually Works

  1. InnoDB locks are attached to index records, not abstract "rows" — every lock is really a lock on an entry in some B+ Tree (usually the clustered index).
  2. Record lock: locks a single index entry.
  3. Gap lock: locks the gap between index entries, preventing new rows from being inserted into that range — this is what blocks phantom inserts.
  4. Next-key lock: a record lock plus the gap immediately before it — InnoDB's default locking strategy for REPEATABLE READ, combining both.
  5. An UPDATE/DELETE with a WHERE clause on an unindexed column locks every row it scans (since there's no index to narrow the walk) — far more locking than expected.
Interview trap

"If I UPDATE one row with a WHERE clause, does it only lock that one row?" — Only if that column is indexed. Without an index, MySQL must scan (and lock) every row it examines to find matches, which can lock far more than the one row you intended.

05

Row Lock

A lock held on individual index records rather than the whole table. InnoDB's default and primary locking granularity — this is what enables high concurrency, letting unrelated rows be modified simultaneously by different transactions.

row 1
X-locked
row 2
free
row 3
S-locked
row 4
free
row 5
X-locked

Other transactions can freely touch rows 2 and 4 while rows 1, 3, and 5 are locked — this per-row independence is the whole point of row-level locking.

Interview one-liner

"InnoDB uses row-level locking by default; MyISAM (an older, less-used engine) only supports table-level locking — this is one of the core reasons InnoDB is the default engine today."

06

Table Lock

A lock held on the entire table, blocking other transactions from touching any row in it — far coarser than a row lock.

LOCK TABLES employees WRITE;
-- exclusive access to the whole table
UNLOCK TABLES;

When table locks still happen in InnoDB

  • Explicit LOCK TABLES statements
  • Many DDL operations (e.g. certain ALTER TABLE forms) take metadata/table-level locks
  • The MyISAM storage engine, which has no row-level locking at all
Beginner mistake

Reaching for LOCK TABLES out of habit. In InnoDB it's rarely needed — row locks via transactions and FOR UPDATE almost always give you what you actually want with far less blocking.

07

Deadlock

Two (or more) transactions each hold a lock the other needs, and each is waiting for the other to release it — a cycle of waits with no way out.

Txn A
UPDATE row 1 -- A now holds X-lock on row 1
Txn B
UPDATE row 2 -- B now holds X-lock on row 2
Txn A
UPDATE row 2 -- blocked, waiting on B
Txn B
UPDATE row 1 -- DEADLOCK: waiting on A, which is waiting on B

InnoDB detects this cycle automatically and picks a victim — usually the transaction that has done the least work — to roll back with error 1213: Deadlock found when trying to get lock, letting the other proceed.

Interview one-liner

"A deadlock is a cycle of lock waits. InnoDB's deadlock detector finds the cycle and force-rolls-back one transaction — the application must be written to catch that error and retry."

08

Deadlock Prevention

Consistent lock ordering

Always access/update tables and rows in the same order across every transaction (e.g. always lower account ID before higher) — this alone eliminates most deadlocks.

Keep transactions short

The longer a transaction holds locks, the higher the chance another transaction collides with it — commit as soon as the work is logically done.

Use appropriate indexes

Well-indexed WHERE clauses mean InnoDB locks only the rows it needs, not every row it has to scan.

Application-level retry

Since deadlocks can still occur under load, catch error 1213/1205 and retry the transaction — this is standard practice, not a sign of a bug.

-- Good: both transactions always lock the lower ID first
START TRANSACTION;
SELECT * FROM accounts WHERE id IN (1,2) ORDER BY id FOR UPDATE;
-- proceed with updates in that same, consistent order
Best practice

Design transactions to touch resources in a fixed, agreed order everywhere in the codebase — the single most effective, low-effort deadlock prevention technique.

09

Spring Boot Relation

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT a FROM Account a WHERE a.id = :id")
Account findByIdForUpdate(@Param("id") Long id);

Spring Data JPA maps LockModeType.PESSIMISTIC_WRITE to a SELECT ... FOR UPDATE under the hood. For deadlock retries, Spring Retry's @Retryable(CannotAcquireLockException.class) is a common pattern to automatically retry a transaction that lost a deadlock race.

Interview angle

"How would you handle a deadlock in a Spring Boot service?" — Catch the translated exception (Spring wraps SQL error 1213 as CannotAcquireLockException/DeadlockLoserDataAccessException), and retry the transaction, typically with @Retryable and a small backoff.

11

Advantages · Disadvantages · When to Use / Avoid

Advantages of explicit locking

Prevents lost updates and write conflicts · guarantees a consistent multi-step operation completes safely · row-level granularity keeps unrelated work concurrent.

Disadvantages

Adds waiting/blocking · risk of deadlocks · overly broad locking (table locks, unindexed WHERE) can serialize far more than intended.

When to use FOR UPDATE explicitly

Read-then-write sequences where the read result determines the write (stock checks, balance transfers, seat reservations).

When to avoid heavy locking

Read-only reporting queries · high-throughput read paths where MVCC snapshots already give correct-enough results.

12

Performance Notes, Beginner Mistakes & Best Practices

Performance note

Long-running transactions holding locks are one of the most common causes of production slowdowns — a forgotten open transaction can block many others indefinitely.

Beginner mistake

Using SELECT ... FOR UPDATE everywhere "to be safe." This serializes reads that didn't need protecting and dramatically increases lock contention and deadlock risk.

Beginner mistake

Not handling deadlock exceptions in application code. A deadlock is expected, normal behavior under concurrency — the fix is catching and retrying, not treating it as a bug to eliminate entirely.

Best practice

Keep transactions as short as possible, access resources in a consistent order, index the columns used in locking reads, and build retry logic for deadlock errors into the application layer.

Interview, Scenario & Company Questions

What's the difference between a lock wait timeout and a deadlock?+
A lock wait timeout is one transaction waiting too long for a lock that will eventually free up (no cycle). A deadlock is a genuine cycle of waits that can never resolve on its own — InnoDB detects and breaks it immediately rather than waiting.
Does a plain SELECT (no FOR UPDATE) take a lock in InnoDB's default isolation level?+
No — a plain SELECT under REPEATABLE READ reads from an MVCC snapshot and takes no lock at all; only locking reads (FOR UPDATE / LOCK IN SHARE MODE) and DML take locks.
What is a gap lock?+
A lock on the space between index records, preventing other transactions from inserting new rows into that range — key to preventing phantom reads.
Your application intermittently throws "Deadlock found when trying to get lock." How do you respond?+
Treat it as expected under concurrency: catch the exception and retry the transaction. Separately, review the transaction's lock acquisition order across the codebase to reduce how often it happens.
A batch job updates thousands of rows and is blocking all other writes to the table. Why, and what's the fix?+
Likely a long-running transaction holding many row locks (or an unindexed WHERE clause locking far more rows than intended). Fix by batching the update into smaller committed chunks and ensuring the WHERE clause is indexed.

[Zoho / Product companies] How would you design a "buy last item in stock" feature to avoid overselling?+
Wrap the stock check and decrement in one transaction using SELECT ... FOR UPDATE on the inventory row, so a second concurrent buyer's transaction waits until the first commits or rolls back.
[TCS Digital / Infosys] Explain shared vs exclusive locks with a simple example.+
Multiple people can read (S lock) a document at once; only one person can edit (X lock) it, and while someone is editing, no one else can even read the in-progress version through a locking read.
[Accenture / Capgemini / Cognizant] What causes a deadlock and how does MySQL resolve it?+
Two transactions acquiring the same two resources in opposite order, each waiting on the other. InnoDB's deadlock detector spots the wait cycle and rolls back the transaction with the least work done, letting the other proceed.

Memory Tricks

S = Share, X = eXclude

Shared lock lets others in. Exclusive lock excludes everyone else, even other readers with a locking read.

Deadlock = "circle of waiting"

Picture two people each holding a door the other needs open — neither can move.

Prevention = "always same order"

If everyone always grabs resources alphabetically/by ID, no cycle can ever form.

Summary

Locks are how InnoDB enforces isolation guarantees in practice. Shared locks allow concurrent reads; exclusive locks are needed for writes and block everything else. InnoDB defaults to fine-grained row locks (via record, gap, and next-key locks on index entries), unlike MyISAM's table-only locking. A deadlock is a cycle of lock waits, automatically detected and broken by rolling back the cheaper transaction. Prevention comes from consistent lock ordering, short transactions, good indexing, and application-level retries.

Revision Notes

  • Shared (S) lock: many readers OK. Exclusive (X) lock: one writer only, blocks everyone.
  • Row lock = fine-grained, high concurrency, InnoDB default
  • Table lock = coarse, blocks entire table, used by MyISAM or explicit LOCK TABLES
  • Gap lock + record lock = next-key lock, blocks phantom inserts
  • Unindexed WHERE in UPDATE/DELETE locks every scanned row
  • Deadlock = cycle of waits; InnoDB auto-detects and rolls back one side (error 1213)
  • Prevention: consistent access order, short transactions, proper indexes, retry logic
