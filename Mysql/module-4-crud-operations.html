01 · Statement · Create

INSERT

The "C" in CRUD — the only way new rows enter a table.

Simple

INSERT adds a new row of data into a table, one occupant moving into a room you already built.

Interview framing

Interviewers check whether you know the difference between naming columns explicitly (safe) vs relying on column order (fragile), and whether you know multi-row INSERT for performance.

insert.sql
-- Single row, explicit columns (always prefer this)
INSERT INTO employees (first_name, email, salary, dept_id)
VALUES ('Asha', 'asha@corp.com', 55000.00, 2);

-- Multi-row insert -- one round trip, much faster than N single inserts
INSERT INTO employees (first_name, email, salary, dept_id) VALUES
  ('Ravi', 'ravi@corp.com', 48000.00, 1),
  ('Meera', 'meera@corp.com', 61000.00, 2);

-- Insert or update on duplicate key (upsert)
INSERT INTO employees (id, email) VALUES (1, 'new@corp.com')
ON DUPLICATE KEY UPDATE email = VALUES(email);
→ 3 rows inserted, 1 upsert applied
→ Query OK: AUTO_INCREMENT advances even on failed/rolled-back inserts (gaps are normal)

01How MySQL works internally

1

Constraint validation

NOT NULL, UNIQUE, FK, and CHECK constraints are validated before the row is written.

2

Row written to InnoDB buffer pool

The row is placed into the clustered index (primary key order) in memory first.

3

Redo log + binlog written

InnoDB writes to its redo log for crash recovery; MySQL writes to the binary log for replication.

4

Secondary indexes updated

Any indexes on other columns (like email) get new entries pointing back to the primary key.

Beginner mistake

Writing INSERT INTO employees VALUES (...) without naming columns. If someone later adds a column, every old INSERT statement silently breaks or inserts into the wrong columns.

Best practice

Batch multi-row inserts instead of looping single inserts from Java — each round trip has network + transaction overhead. In Spring Data JPA, this maps to saveAll() with batching enabled via spring.jpa.properties.hibernate.jdbc.batch_size.

02Interview questions

Why should you always list column names in INSERT?+

Because relying on the table's physical column order is fragile — any future ALTER TABLE that adds/reorders columns can silently corrupt data mapping.

Scenario: You need to insert a row only if it doesn't already exist by email, otherwise update the salary. Scenario+

Use INSERT ... ON DUPLICATE KEY UPDATE, provided email has a UNIQUE constraint — this performs an atomic "upsert" in one statement instead of a SELECT-then-INSERT/UPDATE race condition.

02 · Statement · Read

SELECT

The most-used statement in all of SQL, and the one MySQL spends the most effort optimizing internally.

select.sql
SELECT id, first_name, salary
FROM employees
WHERE dept_id = 2
ORDER BY salary DESC
LIMIT 5;
→ 5 rows returned in 2ms (using index on dept_id)

01Logical order of execution

This is one of the most valuable things to know cold — SQL is written in one order but executed logically in another:

1

FROM / JOIN

Determine the working set of rows across tables.

2

WHERE

Filter rows before any grouping happens.

3

GROUP BY

Aggregate remaining rows into groups (if used).

4

HAVING

Filter groups (not individual rows).

5

SELECT

Compute the final column list and aliases.

6

ORDER BY

Sort the result set.

7

LIMIT

Trim to the requested number of rows — applied last.

Interview trap

"Why can't you use a SELECT alias inside a WHERE clause?" — Because WHERE is logically evaluated before SELECT computes the alias. You can, however, use an alias in ORDER BY, since sorting happens after SELECT.

02Spring Boot relation

Every findBy...() derived query method or @Query annotation in a Spring Data JPA repository ultimately compiles down to a SELECT like this. Understanding the raw SQL underneath makes debugging slow repository methods far easier.

03 · Clause · Filter

WHERE

Filters rows before they're grouped, sorted, or returned — the difference between reading one row and reading a million.

where.sql
SELECT * FROM employees
WHERE salary BETWEEN 40000 AND 60000
  AND dept_id IN (1, 2)
  AND email LIKE '%corp.com'
  AND phone IS NOT NULL;
→ 4 rows matched all conditions
→ LIKE '%corp.com' cannot use a B+Tree index (leading wildcard) — full scan on that predicate

01Operators cheat table

OperatorMeaningNote
=, !=, <>Equality / inequalityIndex-friendly
BETWEEN a AND bInclusive rangeIndex-friendly on the ranged column
IN (...)Match any in a listIndex-friendly, like multiple ORs
LIKE '%x'Pattern match, leading wildcardCannot use index — full scan
LIKE 'x%'Pattern match, trailing wildcardCan use index (range scan)
IS NULL / IS NOT NULLNull checksNever use = NULL, it always evaluates unknown
Common mistake

Writing WHERE deleted_flag = NULL. In SQL, NULL = NULL is unknown, not true — you must use IS NULL.

Performance note

Applying a function to an indexed column in WHERE (e.g. WHERE YEAR(created_at) = 2026) prevents MySQL from using the index on created_at. Rewrite as a range: WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'.

02Interview questions

Why does WHERE email = NULL never return rows?+

SQL's three-valued logic means any comparison with NULL evaluates to UNKNOWN, not TRUE, so the row is excluded. Use IS NULL instead.

Asked at Capgemini: Why is a leading-wildcard LIKE query slow on a large table? Capgemini+

A B+Tree index is sorted left-to-right by the column's value, so it can only efficiently jump to values matching a known prefix. A pattern like '%corp.com' has no fixed prefix, forcing a full table scan.

04 · Statement · Update

UPDATE

The "U" in CRUD — modifies existing rows in place. The most dangerous statement to run without a WHERE clause.

update.sql
UPDATE employees
SET salary = salary * 1.10
WHERE dept_id = 2 AND salary < 60000;

-- multi-column update
UPDATE employees
SET email = 'asha.k@corp.com', updated_at = NOW()
WHERE id = 3;
→ 6 rows matched, 6 rows changed
→ Row-level locks held on matched rows until COMMIT (InnoDB)
Interview trap

MySQL Workbench's "Safe Updates" mode blocks UPDATE/DELETE without a key-based WHERE clause by default — this is a client-side safety net, not a MySQL server feature, and won't save you when running scripts directly.

Best practice

Before running an UPDATE with a complex WHERE, run the same WHERE inside a SELECT first to confirm exactly which rows will be affected.

01Interview questions

Scenario: You ran UPDATE employees SET salary = 0; by mistake and haven't committed. What now? Scenario+

If autocommit is off and you're inside a transaction, run ROLLBACK; immediately to undo it before it's committed. This is exactly why running destructive statements inside an explicit transaction, and checking the affected row count first, matters.

Can you UPDATE a column using its own current value?+

Yes — SET salary = salary * 1.10 reads the current row value during the update; MySQL evaluates the right-hand side per row before writing the new value.

05 · Statement · Delete

DELETE

The "D" in CRUD — removes rows, one at a time under the hood, respecting triggers, foreign keys, and transactions.

delete.sql
DELETE FROM employees
WHERE dept_id = 4 AND created_at < '2020-01-01'
ORDER BY id
LIMIT 100; -- delete in safe batches on large tables
→ 100 rows deleted (batch 1)
→ Re-run until 0 rows affected — avoids one giant table-locking transaction
Interview tip

This module already covered DROP vs TRUNCATE vs DELETE in depth in Module 03 — for CRUD purposes, remember DELETE is the only one of the three that is DML, supports WHERE, and can be rolled back before commit.

Best practice

On large tables, delete in small batches with LIMIT in a loop rather than one massive DELETE — this avoids long-held locks and huge undo-log growth that can stall other transactions.

06 · Clause · Sort

ORDER BY

Sorts the final result set — applied after SELECT, so column aliases are valid here.

order_by.sql
SELECT first_name, salary * 12 AS annual_pay
FROM employees
ORDER BY annual_pay DESC, first_name ASC;
→ Sorted by annual_pay descending, ties broken by first_name ascending
→ Alias "annual_pay" is valid here because ORDER BY runs after SELECT
Memory trick

"ORDER BY comes last, so it can use what SELECT just made." That's why aliases work in ORDER BY but not in WHERE.

Performance note

ORDER BY on a column with a matching index can avoid MySQL's expensive "filesort" step entirely. Check with EXPLAIN — "Using filesort" in the output means MySQL is sorting in memory/disk rather than reading an already-sorted index.

07 · Clause · Pagination

LIMIT

Caps the number of rows returned — the backbone of pagination in every REST API.

limit.sql
-- page 1: rows 1-10
SELECT * FROM employees ORDER BY id LIMIT 10;

-- page 3 (10 rows per page): OFFSET skips the first 20
SELECT * FROM employees ORDER BY id LIMIT 10 OFFSET 20;
-- equivalent shorthand
SELECT * FROM employees ORDER BY id LIMIT 20, 10;
→ LIMIT 10 OFFSET 20 returns rows 21-30
→ Note: MySQL still scans and discards the first 20 rows internally
Interview trap

Deep pagination like LIMIT 10 OFFSET 1000000 is slow because MySQL still has to read and discard a million rows before returning the page. The fix used in production: keyset pagination — WHERE id > last_seen_id ORDER BY id LIMIT 10 — which jumps straight to the right spot using the index.

Spring Boot relation

Spring Data JPA's Pageable/PageRequest compiles down to exactly this LIMIT/OFFSET pattern by default. For very large datasets, teams often switch to Slice with keyset-based queries instead of offset pagination.

08 · Clause · Dedupe

DISTINCT

Removes duplicate rows from a result set — applied across the full selected column list, not just one column.

distinct.sql
SELECT DISTINCT dept_id FROM employees;

-- DISTINCT applies to the whole row of selected columns, not each individually
SELECT DISTINCT dept_id, first_name FROM employees;
→ First query: unique dept_id values only, e.g. 1, 2, 4
→ Second query: unique (dept_id, first_name) pairs — two Ashas in different depts both appear
Common mistake

Assuming SELECT DISTINCT a, b deduplicates on column a alone. It actually deduplicates on the combination of every selected column.

Performance note

DISTINCT often requires MySQL to sort or hash the result set internally to detect duplicates — on large unindexed result sets this can be as costly as an ORDER BY. Prefer GROUP BY when you also need aggregates, since the optimizer can plan for both together.

01Interview questions

Does DISTINCT ignore NULLs?+

No — DISTINCT treats all NULLs in a column as equal to each other for de-duplication purposes, so a column with five NULLs and DISTINCT applied returns just one NULL row.

09 · Syntax · Naming

Aliases

Temporary names for columns, expressions, and tables within a single query — pure readability and reuse, no effect on the underlying schema.

aliases.sql
-- Column alias
SELECT first_name AS name, salary * 12 AS annual_salary
FROM employees;

-- Table alias, essential for joins and self-joins
SELECT e.first_name, d.dept_name
FROM employees e
JOIN departments d ON e.dept_id = d.id;

-- Self-join needs aliases to disambiguate the same table twice
SELECT emp.first_name AS employee, mgr.first_name AS manager
FROM employees emp
JOIN employees mgr ON emp.manager_id = mgr.id;
→ AS is optional in MySQL for column aliases ("first_name name" also works) but recommended for clarity
→ Table aliases are mandatory for self-joins — the parser can't otherwise tell the two references apart
Interview tip

Explain WHY aliases matter beyond shorter typing: they make multi-table JOINs unambiguous, enable self-joins, and give computed/aggregated columns a clean name for the client (Java DTO field, JSON key) to map onto.

01Interview questions

Why can't you use a SELECT alias in the WHERE clause?+

Because of SQL's logical execution order, WHERE is evaluated before SELECT computes the alias — the alias simply doesn't exist yet at that stage. It's valid in ORDER BY and HAVING, which run afterward.

Why are table aliases required for a self-join?+

A self-join references the same table twice in one FROM clause. Without aliases, MySQL cannot distinguish which occurrence a column reference belongs to.

Wrap-up

Summary & Revision Notes

INSERT

Always name columns explicitly; batch multi-row inserts for performance.

SELECT + WHERE

WHERE runs before SELECT logically — aliases aren't visible there yet.

UPDATE / DELETE

Always test the WHERE clause with a SELECT first; never run without WHERE on a live table.

ORDER BY + LIMIT

ORDER BY sorts, LIMIT trims — both run near the very end of logical execution.

DISTINCT

Deduplicates on the full combination of selected columns, not just one.

Aliases

Required for self-joins, essential for readable multi-table queries and clean API field names.

Before your interview

Be ready to explain SQL's logical execution order out loud, write a paginated + sorted + filtered SELECT from scratch, and justify why you'd never run UPDATE or DELETE without a tested WHERE clause.
